## D-001 采用纯前端静态架构，不建网站后端

- **背景**：工具面向个人 / 小团队的 offer 名单复盘，输入含姓名、薪资等敏感信息。
- **决策**：Vite 构建出 `dist/` 静态目录，部署到 GitHub Pages / Cloudflare Pages / Vercel 任一
  静态托管；**不创建** Functions、API Routes、数据库连接、上传接口或登录系统。
- **理由**：数据不出浏览器最省心；无后端即无服务器侧数据留存与运维面。
- **被否决**：自建后端做报告生成、云数据库做多人协作、云账号做权限管理（PRD 3.3 明确不做）。
- **影响**：所有解析、清洗、统计、加密必须在浏览器内完成，长任务放入同源 Web Worker。

## D-002 默认本地处理；DeepSeek 为逐次确认的可选例外

- **背景**：V1.0 要求完全不调用云 AI；V1.1 改为「默认本地 + 确认后可选聚合分析」。
- **决策**：
  1. 默认路径对 DeepSeek **零请求**（启用开关、存 Key、导入、切筛选、看历史都不发请求）。
  2. 唯一入口：看板右上角「AI 深度分析」→ 本地生成聚合摘要 → 严格脱敏 → **完整预览** →
     用户**逐次确认** → 唯一 network adapter 直连 `https://api.deepseek.com`。
  3. 只发聚合摘要，任何明细（含换代号的逐行数据）都禁止发送。
  4. 两条 CSP 构建配置：仅本地版 `connect-src 'none'`；可选 AI 版精确允许
     `https://api.deepseek.com`，不允许 `*` 或任意 `https:`。
- **理由**：既保住「默认不外发」的安全叙事，又让用户能按需获得 AI 解读。
- **被否决**：完全禁用云 AI（与 V1.1 冲突）；默认开启 AI；后台预取 / 自动探活 / 自动重试；
  网站运营方托管的转发代理。
- **已知限制**：Key 在认证时必须发给 DeepSeek，因此**不能**宣称「Key 绝不离开浏览器」；
  清除本地数据**不能**撤回已发送内容；供应商保留策略以其官方条款为准。

## D-003 技术栈：React + Vite + TypeScript strict + Tailwind v4

- **决策**：React + Vite（Node 20.19+/22.12+，本机 Node 24.19.0 满足）+ TypeScript strict
  + Tailwind CSS v4（`@tailwindcss/vite` 插件 + `@import "tailwindcss";`）。
- **理由**：纯静态、生态成熟、类型安全；Tailwind v4 的 Vite 插件式集成最简。
- **被否决**：Next.js / Nuxt 等含服务端能力的框架（会引入后端面）；Tailwind v3 的 PostCSS 旧配置。
- **影响**：步骤1 安装时按官方文档核实版本并提交锁文件，**不混用不同 Tailwind 主版本配置**。

## D-004 统一指标引擎，公式只实现一次

- **决策**：所有计数、率、周期、分位、去重、基准范围在 `domain` 层纯函数实现；
  组件只消费结果，不重写公式。
- **理由**：PRD 第 6 章要求同一数据 / 配置得到一致结果，且每个指标必须能追到分母。
- **被否决**：在图表组件里各自计算（会造成率与分母不一致）。
- **影响**：步骤7 先交付引擎并用 PRD 12.2 的合成验收集验证，再写页面。

## D-005 加密持久化：PBKDF2-SHA-256 + AES-GCM-256 写入 IndexedDB

- **决策**：Dexie 存加密信封；密码派生密钥，随机 salt ≥16 字节、每次加密唯一 12 字节 IV、
  128 位认证标签；AAD 绑定仓 ID 与版本；KDF 迭代次数做本机基准后持久化（初始建议 600,000）。
- **理由**：PRD 10.3；生产版不提供默认明文落盘。
- **被否决**：只做 localStorage 混淆；保存密码哈希当加密；把密钥持久化。
- **已知限制**：解锁后恶意扩展 / XSS / 已被控制的设备仍可读取；不承诺取证级内存擦除；
  不承诺数据永久保留（浏览器可能回收存储）。

## D-006 导出先脱敏：唯一 SanitizedReport 模型

- **决策**：所有导出格式都从唯一脱敏快照生成；明细默认不导出，薪资只出区间，

## D-018 取值映射口径：缺失一律 `null` / 「未知」，绝不写 0

- **决策**（`src/domain/valueMappings.ts` 是唯一实现，其他步骤不得各自判断）：
  - 空值、`-`、`/`、`无数据`、`#N/A` 等占位符 → 金额 `null` / 文本「未知」，**绝不**写成 0；
  - 房补：「无（本地院校）」等是**已知取值** `无补贴`（`housingAmount = 0`）；缺失 / 无法识别是「未知」（`housingAmount = null`）；
    「长期住宿 / 提供住宿」是独立类型且**永不折算**为现金（同现时按最保守处理并要求确认）；
  - offer 状态：原值「已送审批」→ `offer审批中`（A），计入 N、**不**计入核心分母 D；未识别的非空值 → `未知` + `UNKNOWN_ENUM_VALUE` 提示；
  - 「替补/替换」保留未拆分枚举 `替补替换未拆分`，不自动拆分；需求 ID 一律按字符串处理并保留前导 0；
  - 三值字段（是否 GPT 来源）：缺失 / 无法识别 = `null`，**不得**当作「否」；
  - 薪资：只解析单一数值；区间（如 `1000~2000`）不取中点、不推断币种与计薪周期，保持 `null` 并要求确认；
  - 唯一键只能是本地生成的 `recordId`，姓名 / 需求 ID / 推荐人禁止作为身份键（`IDENTITY_RULES`）。
- **理由**：这些都是 PRD 的硬口径；写 0 或猜单位会让低薪标签、待遇对比与核心率全部失真。
- **影响**：步骤5 清洗与步骤7 指标必须复用这些解析结果，不得重新实现；扩充别名只改映射表，不改返回值语义。

## D-021 导入上限：拒绝并说明，绝不静默截断

- **决策**（`src/importers/limits.ts`）：
  | 项目 | 上限 | 超限处理 |
  |---|---|---|
  | 文件大小 | 20 MB | 读取**之前**拒绝（不分配内存） |
  | 粘贴字符数 | 2,000,000 | 拒绝并提示分批粘贴 |
  | 数据行数 | 50,000 | 解析中立即中止（PapaParse `abort`）并报实际值 |
  | 列数 | 512 | 同上 |
  | 单元格总数 | 2,000,000 | 同上 |
- **理由**：上限只为「不冻结界面、不 OOM」，不代表业务规模。截断会让统计悄悄少数据，比直接报错更危险；
  因此一律给出「上限值 + 实际值 + 下一步建议」，且错误信息只含数值与行号，不含单元格内容。
- **影响**：超限对应 `LIMIT_EXCEEDED`（阻断级，停止导入，不破坏已有数据）。数值是保守的工程判断，
  后续如有真实规模数据可调整常量，但**不得**改成截断。

## D-022 解析阶段口径：只取值、不排除、缺失即 null、行号可回溯

- **决策**（`delimited.ts` / `xlsx.ts` / `grid.ts` / `pipeline.ts`）：
  - **只读值与已有缓存**：SheetJS 用 `cellFormula: true` 仅为识别「有公式但无缓存结果」（提示转值后重传），
    永不计算公式、不执行宏、`cellHTML: false` 不解析 HTML、不激活单元格链接、不联网更新；
  - **日期数字序列不转换**（`cellDates: false`）：1900/1904 与歧义日期属清洗步骤5，本步只读原值并记录
    `date1904`；需求 ID 等文本永不当日期；
  - **隐藏行 / 列不默默排除**：隐藏行默认包含（`hidden` 标记 + 计数），只有用户在界面显式勾选
    「排除隐藏行」才不进 `rows`；隐藏列只记录下标，列数据一律保留（避免表头与单元格错位）；
  - **空单元格 = `null`**：CSV 空字段、XLSX 无单元格、空字符串单元格、错误单元格无文本都统一为缺失，
    绝不用 0 / 空字符串冒充；错误单元格保留可读错误码（如 `#DIV/0!`）供清洗阶段按字段错误处理；
  - **空行保留并计数**（`emptyRow` + `emptyRowCount`）；仅丢弃「文件末尾换行产生的那一个全空行」；
  - **物理行号可回溯**：CSV / 粘贴用 PapaParse `meta.cursor` 换算物理行（字段内换行不会错位），
    XLSX 用工作表行号（`range.s.r + 1` 起）；
  - **空表跳过并提示**（`EMPTY_SHEET_SKIPPED` 警告）；整个来源无可用数据行 → `EMPTY_DATASET`（阻断）；
  - 读取阶段的问题码只记行号与代码，**绝不含整行内容**。
- **理由**：PRD 5.1 与 12.3 A01/A02 的硬要求；任何「顺手清洗」都会让原值不可回溯，并污染后续指标口径。
- **影响**：清洗阶段（步骤5）必须基于本步输出的 `RawSheet`（原值 + 行号 + 来源）实现，不得重新读文件。

## D-023 解析在 Worker 执行；桶文件不导出重模块（首屏包与解析库解耦）

- **决策**：
  - 解析走**同源 Worker**：`new Worker(new URL('../workers/parse.worker.ts', import.meta.url), { type: 'module' })`，
    Vite 打包为独立 chunk；消息一律带任务 ID，支持进度、取消与「过时结果丢弃」（新任务到达即取消旧任务，
    取消后到达的响应直接丢弃）；UI 只显示阶段与比例，绝不打印整行数据；
  - **取消不改变已有数据**：取消只丢弃这一次解析的结果，界面保留上一次的成功结果；
  - 无 Worker 环境（Node 单测、极旧浏览器）回退到进程内实现，解析依赖用**动态 `import()`** 加载；
  - 因此 `src/importers/index.ts` **刻意不导出** `pipeline` / `delimited` / `xlsx` / `workerBridge`
    （它们会牵入 SheetJS 与 PapaParse）；需要时按文件路径 import（测试即如此）。
- **理由**：大文件不能冻结 UI（PRD 5.1 / 10.4），同时首屏包只有界面与轻量契约。
  实测（最终构建）：首屏 `index-*.js` 320.13 kB（gzip 102.66 kB）、Worker chunk 419.05 kB、
  回退 chunk 391.54 kB；若桶文件导出重模块，首屏包会变成 712 kB（约 236 kB gzip），Vite 也会报「动态 import 失效」。
- **影响**：新增解析相关工作必须放进 Worker 或动态 import 路径；构建时留意 Vite 的
  `INVALID_DYNAMIC_IMPORT` 警告——出现它说明有人又把重模块加回了桶文件。
  打包后的 PapaParse 内含一条「远程文件」的 `XMLHttpRequest` 代码路径（我们只传字符串、
  从不设置 `download`，因此不可达）；步骤13 的 CSP `connect-src 'none'` 会进一步封死它。

## D-024 映射契约扩展：扩展列目标、显式合并规则、模板命中级别

- **决策**（步骤4，`src/domain/types.ts` + `src/domain/fields.ts` + `src/domain/mapping.ts`）：
  - `ImportMappingEntry` 增加 `targetExtension: ExtensionFieldKey | null`（与 `targetField` **互斥**）：
    PRD 4.3 允许把多余列映射到已定义的扩展列，扩展列是独立键空间，不能与 21 个标准字段混用同一个字段；
    两个都为 `null` 即「忽略该列」，未映射的列不参与分析、不进入导出；
  - `ImportMapping` 增加 `merges: MappingMergeRule[]`：登记「按列顺序取第一个非空值」的显式合并规则
    （只记列下标与目标，**不存任何单元格值**；取值由步骤5 执行）；
  - `COLUMN_MATCH_LEVELS` 增加 `template`：命中用户已确认的映射模板记为 `template`
    （PRD 4.3 的第三优先级是「用户已确认的别名模板」），与人工改写的 `manual` 分开，便于回溯「这条映射从哪来」；
  - `MappingDecisions` 分成 `overrides`（人工改写）与 `templateOverrides`（模板套用）两个来源，
    界面状态只有这一份决策对象，其余（最终 entries、冲突、缺列、禁用模块、可否提交）全部由
    `applyMappingDecisions(plan, decisions)` 纯函数推导。
- **理由**：步骤2 定义契约时还没有消费者，步骤4 是第一个消费者；把「扩展列目标」「显式合并」
  「模板来源」写进契约，才能满足 PRD 4.3 的「不静默覆盖」与「可回溯」，也避免步骤5 再改结构。
- **影响**：步骤5 起消费 `ImportMapping` 时必须处理两类取值：单列取值与 `merges` 的 `first-non-empty`；
  扩展列值写入 `NormalizedRecord.extensions`，不得混入标准字段。

## D-025 解析结果与映射草稿只驻内存；映射模板只提供结构与版本接口

- **决策**（步骤4，`src/storage/sessionStore.ts`）：
  - 步骤3 的 `RawSheet`、映射页的编辑草稿、已确认的 `ImportMapping`、以及本会话的映射模板
    统一放在**模块级内存会话**（`getImportSession` / `setImportSheet` / `saveMappingDraft` /
    `confirmImportMapping` / `clearImportSession`），跨页面读取，**不落任何明文盘**：
    不使用 IndexedDB / localStorage / sessionStorage / Cache / Cookie，不打印日志，不挂 `window`；
  - `setImportSheet(新表)` 会清空旧草稿与旧确认（旧映射针对旧表，不得张冠李戴）；
    「重新选择来源」等价于放弃当前解析结果（映射模板属于配置，保留）；
  - 映射模板只提供**结构 + 版本接口**：`buildMappingTemplate` / `applyMappingTemplate` /
    `serializeMappingTemplate` / `parseMappingTemplate`（严格校验：结构版本不符、出现
    `samples` / `values` / `rows` / `cells` / `data` 等键、字段键非法即拒绝）；
    模板里没有存放单元格取值的字段，模板按**规范化表头名**复用而不是按列顺序；
  - 文件下载 / 上传与加密持久化**不在本步实现**：由步骤6（加密仓）与步骤12（备份 / 映射模板管理）接入，
    届时只需替换 `sessionStore` 的读写实现，界面调用方式不变。
- **理由**：PRD 10.2 的默认模式就是「临时模式，只在内存，刷新即丢失」；PRD 4.3 明确
  「返回导入页可保留临时映射但不得落明文盘」，因此在加密仓可用之前不允许任何形式的持久化，
  也不做「先存 localStorage / JSON 导出」的折中。
- **影响**：刷新（F5）会丢失解析结果与映射草稿，这是**预期行为**，界面文案必须如实说明
  （导入页与映射页都已标注「只在内存、刷新即清除」）；
  在步骤6 落地前，不要在任何地方缓存 `RawSheet` 或映射草稿到浏览器存储。

## D-027 加密仓分层：懒门面 + 桶文件不导出 Dexie 重模块（步骤6）

- **决定**：`src/storage/vaultFacade.ts` 导出的 `encryptedVault` 是**界面唯一入口**：方法体里
  `await import('./vault')` / `import('./backup')`，类型全部用 `import type`（编译期擦除，不产生运行时依赖）；
  `lock()` 例外，走纯逻辑模块（`keys` / `vaultEvents`）**不加载任何 chunk**，保证「锁定」这条安全路径永不失败。
  `src/storage/index.ts` 只导出契约与纯逻辑（`errors` / `idleLock` / `quota` / `sessionStore` / `vaultEvents` /
  `vaultMeta` / `vaultSession`）+ `export { encryptedVault }` + `export type`，**不**静态导出 `vault.ts` /
  `backup.ts` / `db.ts`。组件（含页面）不得静态 import 这三者。
- **理由**：与 D-023（解析器不进首屏包）同源。Dexie 约 100 kB，静态引入会把首屏包从 421 kB 顶到 520 kB 以上，
  而「有没有本地仓」这件事在临时内存模式下根本不需要。让「重实现只出现在懒边的另一侧」成为可机械检查的约束，
  比事后靠人记住更可靠。
- **证据**：`npm run build` 117 modules，首屏 `index-*.js` 421.09 kB（gzip 129.23 kB），
  `vault-*.js` 102.80 kB 与 `backup-*.js` 4.11 kB 为独立按需 chunk，无 `INVALID_DYNAMIC_IMPORT` 警告。
- **影响**：新增存储能力必须同时改门面与桶文件；新增页面若静态引入 `./vault` 会立刻在构建产物里显形（首屏体积），
  评审时按此判断。

## D-028 信封与 KDF 参数：一次派生两把不可导出密钥，解析严格、不降级（步骤6）

- **决定**：PBKDF2-HMAC-SHA-256；初始迭代 **600,000**（合法区间 100,000–2,000,000，
  `recommendKdfIterations` 提供本机基准后的推荐值），参数随仓元数据**持久化**；salt 每个仓 16 字节；
  一次派生 64 字节切成 `dataKey`（业务对象）与 `secretKey`（秘密槽位）两把 AES-GCM-256 密钥，
  `extractable: false`；每次加密**独立 12 字节 IV**，AAD 绑定（仓 ID + revision + 用途字符串），
  认证标签 128 位。`parseKdfParams` / `parseEncryptedEnvelope` 对格式版本 / 算法 / 迭代数 / 长度 / base64
  一律**严格拒绝**（例如迭代数 1,000 **不**当默认值用）。仓里**不存密码哈希**，解锁靠「用数据密钥解密固定校验串」。
- **理由**：PRD 10.3；与 D-005 的口径一致（PBKDF2-SHA-256 + AES-GCM-256 信封写 IndexedDB，明确否决「保存密码哈希当加密」与「只做 localStorage 混淆」），本步是把 D-005 落地成可测试的实现。
- **影响**：密码错误、密文被篡改 / 截断 / 结构非法在 `CryptoError` 层**不区分原因**，界面统一文案；
  KDF 参数升级走新的格式版本 + 显式迁移提示，不静默重新派生；新增用途必须加进 AAD 用途表，否则解密失败。

## D-029 解锁 / 锁定与闲置计时：单一应用级会话守卫（步骤6）

- **决定**：`App.tsx` 用 `useEffect(() => mountVaultSession(), [])` 只挂一次守卫。解锁 → 从仓元数据同步
  `idleLockMinutes`（默认 15，合法 1–120）并启动 `idleLock` 计时；闲置到点 → `lockActiveVault('idle')`；
  锁定 / 清空 / 会话过期（其他标签页改密）→ 丢弃内存密钥 + 清空内存业务数据（`clearImportSession`：
  `RawSheet`、映射草稿、已提交数据集），但**保留**与数据无关的配置（清洗设置草稿、本会话映射模板）。
  界面只能通过 `activeVaultSessionGuard()` / `readVaultIdleRemainingMs()` 读取倒计时，**不得**自建计时器；
  倒计时是渲染时读取 + 每秒一次重渲染触发，而不是在 effect 里 setState。
- **理由**：两份计时器就是两份真相（一个页面点过鼠标而另一个不知道，就会过早或过晚锁定）；
  纯逻辑计时器可以用假时钟做确定性测试，避免「等 15 分钟」这种没法进 CI 的验证。
- **影响**：新增页面不得自带闲置计时；「活动」只在守卫层统一重排（1 秒节流，唤醒后二次核对）；
  锁定后的界面必须按「没有数据、没有 AI Key」展示，不得残留上一次解锁的读数。

## D-030 AI Key 用独立密钥、独立表，普通备份排除秘密槽位（步骤6）

- **决定**：
  - 物理上分表：`objects`（业务对象 / 分析缓存）与 `secrets`（秘密槽位）两张表，
    秘密槽位目前只有 `ai-api-key`（`VAULT_SECRET_SLOTS`），新增槽位必须同时更新枚举与备份 / 清除口径；
  - 密钥上分层：`secretKey` 与 `dataKey` 由同一次 PBKDF2 派生但**切分使用**，
    AI Key 的密文与业务数据密文不共用同一把密钥；
  - 生命周期独立：清空 AI 历史（`objects`）**不**动秘密槽位；删 Key 只删槽位（`deleteVaultSecret` /
    `clearVaultSecrets`），业务对象与分析缓存不受影响；
  - 普通备份只读 `objects`，`includesSecrets` 恒为 `false`，恢复后必须重新填写 Key。
- **理由**：PRD 10.3 / 10.5 与 AGENTS §2.2「Key 只在本地，不得进入普通备份」；
  「清数据顺手把 Key 也删了」和「备份文件里带着 Key」都是用户预料不到的破坏 / 泄漏。
- **影响**：AI 步骤与步骤12 的「删除 / 清除」按钮必须按这张表拆分动作并在文案里写明互不代替；
  `VaultManagerPanel` 只显示「是否已保存 Key」，不解锁就不显示（避免锁定态残留读数）。

## D-031 忘记密码只有两条路；错误文案不区分「密码错」与「密文被改」（步骤6）

- **决定**：本地仓**不保存密码哈希、也没有任何找回接口**；设置页在解锁失败处只给两条路——
  「用加密备份恢复」「清空整个本地仓重建」，后者属于危险操作，必须输入自定义口令二次确认
  （`PhraseConfirm`），且清空会同时删除元数据、业务对象与秘密槽位。
  `vaultErrorMessage` 把「密码不正确」「密文被篡改 / 截断」「结构非法」「版本不支持」收敛成固定文案，
  底层 `CryptoError` / Dexie 的 message 一律不出现在界面上。
- **理由**：AGENTS §2.4（「不提供密码找回」）与 PRD 10.3（加密设计：只存 KDF 参数与密文）；区分原因既会让人误以为「密码接近正确」而反复试探，
  也给攻击者一个反馈信道；对用户来说「解不开」这件事的处置方式本来就一样。
- **影响**：新增错误码必须在 `vaultText.ts` 里映射到固定文案，不得把原始 message 透传到 UI；
  清空 / 改密等破坏性操作必须保留二次确认，不得为了「顺手」做成单击生效。

## D-033 率一律带分子分母与排除数；分母为 0 给 null，汇总率合计后相除（步骤7）

- **决定**：
  - 所有率 / 占比统一用 `RateMetric`（`numerator` / `denominator` / `value` / `excludedCount` / 中文 `note`），
    由唯一的 `rateOf` 构造；`denominator === 0` 时 `value = null`（界面显示「—/无有效样本」，**不显示 0%**）。
  - 核心率分母固定 D = J + P + R；「审批中占比 A/N」「待入职占全部 P/N」「状态结构占比 各状态/N」是
    **另一类分母**，单独构造并在 `note` 里写明「分母为 N，与核心率分母不同」，不允许与核心率混排成一个数字。
  - 汇总率必须由**合计后的分子分母**相除（`summarizeRecords` / `topNWithOther` 都重新汇总），
    禁止平均各分组百分比；`topNWithOther` 的「其他」组也按此法重算。
  - 原因填写率的分母**仅** R：非拒 offer 不进分母（计入 `excludedCount`），「未填写」仍计入分母，
    所以原因全缺失时结果是 0%（与「薪资基准 n < 5 显示 null」不是同一类情况，两者不可互相套用）。
  - 自动结论门槛 `AUTO_CONCLUSION_MIN_DENOMINATOR = 10` 只在引擎里定义一次；`sufficient` 的文案
    必须同时说明「不代表统计显著」。
- **理由**：PRD 6.1 的处理规则与 12.2 的验收都要求「能看到分母」；把分母选择权留给页面，
  必然出现「同样的 40% 两个页面口径不同」。
- **影响**：KPI 卡片、分组表、报告与 AI 摘要都必须渲染 `numerator` / `denominator` / `excludedCount`；
  小样本（0 < D < 10）必须显示标注且不参与自动排名。

## D-034 周期分三种口径；拒 offer 的历史等待时长一律未知（步骤7）

- **决定**：
  - 实际招聘周期：仅「已入职」，`入职日期 − 启动日期`，日历日、合法且非负（`null` 不当 0 天）；
    清洗层已算出的 `derived.recruitmentCycleDays` 优先，缺失时才由引擎按日期重算。
  - 待入职计划周期：仅「待入职」，用「入职时间」列的计划日期，**单独统计、单独展示**；
    计划日期早于启动日期时不可用（清洗层原来只判「有日期」，引擎收紧为「日期差合法非负」）。
  - 预计实习天数（预计离职 − 入职）只作计划口径，不能称实际留存。
  - 等待时长：已入职=实际周期；待入职 / 审批中=`截至日 − 启动日`（只能叫「当前等待时长」）；
    拒 offer / 其他 / 未知=**未知**（附件缺拒绝日期，绝不拿计划入职日推算决策耗时）。
    `isWaitingTooLong` 在天数未知时返回 `null`，**不**当「未超时」。
- **理由**：PRD 6.1 / 9.3 的红线；三类周期混在一起会直接产生「用计划日期得出了历史结论」的错误。
- **影响**：`decorateRecords` 会覆盖清洗层的 `plannedCycleEligible`（收窄为「计划周期合法可用」），
  步骤8 起的界面必须用 `actualCycleStats` / `plannedCycleStats` 两个独立区块展示，不得合并成一个「平均周期」。

## D-035 同岗基准：严格同组、参照集合默认不受筛选影响、n ≥ 5 才出分位（步骤7）

- **决定**：
  - 组键 = 城市 + 序列 + 规范化岗位 + 币种 + 计薪周期，用控制字符分隔并在取键前剔除控制字符；
    任一组件缺失 /「未知」/「其他」，或币种与计薪周期未确认（`null` /「其他」）→ **不出基准**。
    「未知」与「其他」都是合并桶，无法保证严格同组，宁可显示「同岗样本不足」也不给错误的低薪标签。
  - 参照集合默认 = 当前数据集全部保留记录中有效薪资的记录（`scope = 'dataset'`），
    **不受渠道 / HR / offer 状态 / 薪资筛选影响**；显式换范围必须传 `referenceRecords` 并把
    `scope` 标为 `userDefined` 且随报告记录；`benchmarkScopeNote` 负责把这段口径变成可显示文本。
  - `n ≥ 5`（`DEFAULT_BENCHMARK_MIN_SAMPLE`）才计算 P25 / P50 / P75；不足时 `sufficient = false`、
    分位为 `null`、`isBelowMedian` 为 `null`（**不打低薪标签**）；不自动扩展到不同岗位 / 城市。
  - 百分位排名用并列中位秩，并以**比率**（0–1）返回，与全部率保持同一写法；`低于中位数 = salary < P50`，
    相等不标低；样本含自身，属描述性定位，不是概率。
  - 「薪资 + 现金房补」只在同币种、同周期且金额明确时相加：无补贴按 0 计入；现金房补周期为「次」
    等无法与计薪周期对齐时总额为 `null`；提供住宿不折现；房补缺失或未知**不填 0**。
- **理由**：PRD 6.2 全部条款；基准漂移与「缺失当 0」是这类工具最容易出现的错误结论来源。
- **影响**：步骤9 的薪酬模块必须并排显示「P25/P50/P75 + n + 参照集合说明」；
  低薪标签只在 `isBelowMedian === true` 时出现，`null` 一律显示为「样本不足 / 未知」。

## D-036 分组与筛选用同一套函数；薪资区间边界由调用方显式给出（步骤7）

- **决定**：
  - 14 个维度（城市、渠道、推荐类型、HR、岗位、序列、部门、需求类型、毕业年级、学历、学校、GPT、
    薪资区间、房补类型）共用 `dimensionValueOf` + `aggregateByDimension` + `summarizeRecords`，
    每个分组都带 N/J/P/A/R/D、各率、有效周期 n 与覆盖需求数；缺失 / 不可识别统一归「未知」并保留展示。
  - 筛选：字段间 AND、字段内 OR、未选择=不过滤；「未知」是可选的独立值；状态筛选会改变 D，
    必须给「当前子集率」提示；时间默认不筛选，基准日（启动招聘日期 / 入职日期）必须显示，
    日期缺失单列计数且默认不纳入；去重只排除显式 `removedAsDuplicate` 的行，
    未确认的重复行保留并单独计数（`unconfirmedDuplicateCount`）。
  - 薪资分档只提供 `bandOf(value, edges)` 机制，**引擎内不设默认边界**：分档是业务口径，
    由用户在选择「薪资区间」维度时显式给出，避免领域层凭空发明「3000 一档」这类规则。
- **理由**：PRD 6.3 要求各维度复用同一聚合函数；把分档默认值写进引擎会让「谁定的档」无法追溯。
- **影响**：步骤8 的筛选界面必须传 `salaryBandEdges` 并在界面与报告里显示分档；
  新增维度只需在 `GROUP_DIMENSIONS` 与 `dimensionValueOf` 增加分支，不得另写聚合函数。

## D-037 看板图表用 ECharts，但**必须懒加载**，首屏不得引入（步骤8）

- **决定**：新增运行时依赖 `echarts@^6.1.0`（本地打包，写入 `package.json` 与锁文件；无 CDN、
  无远程脚本、无在线字体）。图表通过 `src/features/dashboard/charts/` 三层接进来：
  - `echartsRegister.ts` 用**官方文档的具名导入**只注册用到的模块（Bar / Line + Grid / Tooltip /
    Legend / Aria + Canvas 渲染器），并且**只能被动态 `import()` 加载**；
  - `echartsLoader.ts` 是唯一入口：静态只 `import type`，运行时 `import('./echartsRegister')`，
    模块级缓存 promise（失败不缓存，允许重试）；
  - `EChart.tsx` 负责 `init` / `setOption(option, true)` / `ResizeObserver` 重排 / 卸载 `dispose`，
    加载中有明确文字、失败有可读提示，并且**图表下方永远渲染同数数据表**。
- **理由**：本应用首屏是导入页，而 ECharts 完整包压缩后仍有数百 kB。若在看板里静态 `import 'echarts'`，
  它会跟着 `App.tsx` 的静态路由一起进入首屏包；`modulePreload.polyfill` 已关闭，
  首屏包一旦包含 ECharts 就等于把「首屏体积」和「离线可用性」一起押在图表上。
  另外实测「在 loader 里 `await import('echarts/charts')` 再访问 `charts.BarChart`」会被保守保留整个
  barrel（多出 parseGeoJson / geo 等约 400 kB 的懒 chunk），因此注册必须写在一个被动态导入的
  **具名导入**模块里。
- **影响**：构建产物实测——首屏 `index-*.js` **461.38 kB**（gzip 140.41；步骤7 为 421.11），
  `echartsRegister-*.js` **536.43 kB 懒加载**（gzip 181.32），`dist/index.html` **没有** ECharts 相关
  preload；构建出现 1 条「chunk > 500 kB」提示，指向该懒 chunk，**不**通过调高
  `chunkSizeWarningLimit` 掩盖。步骤11 的离屏 PNG 导出必须复用同一注册模块，
  不得另起一份 ECharts 引入路径；后续若要再减体积，优先换 SVG 渲染器或深路径导入，
  而不是把 ECharts 挪回首屏。

## D-038 时间趋势落在引擎里：分月聚合只认「合法日期」（步骤8）

- **决定**：新增 `domain/analytics/timeline.ts`：`periodKeyOf` 只接受合法日历日（`2026-02-30` /
  `2026-13-05` 返回 `null`，**不**截前 7 位凑月份）；`aggregateByMonth(records, basis)` 按
  `recruitmentStartDate` 或 `joiningDate` 分月，缺失 / 非法日期**单列计数**、不落进任何月份，
  月份升序，每批复用 `summarizeRecords`；`note`（口径提示）与 `timelineCoversAllRecords`
  （`Σ月份 N + 未纳入数 == 记录总数`）同层提供，界面只展示。
- **理由**：趋势不是 `GROUP_DIMENSIONS` 里的业务维度，用「城市 / 渠道」那类分组函数冒充时间轴会让
  「哪个月」说不清；而「附件没有 offer 发出时间」这条 PRD 6.3 红线必须以**代码里的唯一文案**存在，
  否则每个页面都可能把启动日期写成「发 offer 趋势」。每批复用 `summarizeRecords` 还保证了
  趋势里的 N/J/P/A/R/D 与 KPI 卡片同口径（点开某个批次 Drill-down 后数字对得上）。
- **影响**：界面只能渲染 `timeline.note`，不得自写趋势文案；以后新增时间粒度（周 / 季度）
  必须在本模块加纯函数并补测试，不得在组件里按字符串切日期。

## D-039 看板筛选有独立纯逻辑层；「清空筛选」的清理范围写死（步骤8）

- **决定**：筛选的选择状态、转换与展示辅助集中在 `src/features/dashboard/dashboardFilters.ts`
  （纯函数 + 29 例单测）：选择状态 → `AnalysisFilters`、同字段 OR / 字段间 AND、状态多选与下钻替换、
  时间基准 / 区间 / 「纳入日期缺失」、薪资分档边界解析（**非法片段原样回显**且整份按未配置处理）、
  维度选项清单（未知固定排最后、计数来自传入记录集合）、趋势下钻的月份区间（UTC 算月末）、
  生效筛选描述。「清空筛选」只清**筛选条件**（维度、状态、时间、缺失纳入），
  **保留**时间基准与薪资分档边界（口径配置不是筛选条件）。
- **理由**：这些规则一旦散落在各个下拉框里，同一份筛选在两处会给出不同行为（例如一处静默忽略
  非法日期、另一处按字符串比较）；把规则放进纯函数层才能被测试覆盖。非法输入**不采用**而不是

- **影响**：组件内不得再判断「哪个维度算未知」「日期合不合法」「清空要清什么」；
  新增筛选维度只需在引擎的 `GROUP_DIMENSIONS` 增加取值分支，界面自动出现对应筛选器。

## D-040 AI 入口在步骤8 只做**禁用占位**，不发任何请求（步骤8）

- **决定**：看板右上角渲染「AI 深度分析（后续步骤接入）」按钮，常驻 **disabled**，并写明

## D-041 岗位/序列/部门的「量率散点」用 ScatterChart，但注册只待在懒加载 chunk（步骤9）

- **决定**：步骤9「岗位 / 序列 / 部门」的量率图（横轴核心分母 D、纵轴拒 offer 率、点大小 = 记录数）
  **保留散点图**，为此在 `charts/echartsRegister.ts` 增加 `ScatterChart` 具名导入并注册，
  并把 `ScatterSeriesOption` 并入 `charts/echartsLoader.ts` 的 `EChartOption`（静态只 `import type`）。
- **理由**：PRD 8 章对该模块的红线是「量大入职少 / 拒 offer 高**必须同时**展示 N、D、R 和阈值」。
  一个分组要同时表达「规模（D/N）」与「转化（拒率）」两个测度，柱状图只能表达一个，
  换成柱状图等于把这条口径要求降级成两张互相对照的表；散点才是这一要求的最小正确图表。
  代价可控：ECharts 本来就是懒加载的独立 chunk，散点只让该懒 chunk 增加约 6 kB
  （实测 536.43 → 542.67 kB），**首屏包与 `dist/index.html` 的 preload 列表完全不变**。
- **影响**：仍然**禁止**任何组件静态 `import 'echarts'`；`ScatterChart` 只能出现在
  `echartsRegister.ts`（被动态 `import()` 的那一侧）。以后再加图表类型，走同一条路：
  在注册模块具名导入 + 在 loader 的类型联合里加对应 `XxxSeriesOption`，不得改成
  `await import('echarts/charts')` 再访问属性（rollup 会保守保留整个 barrel）。
  散点数据点由 `dimensionViews.ts` 的 `scatterPointsOf` 生成，组件不算坐标。

## D-042 分维度分析有独立纯逻辑层；合并行既不下钻也不进散点（步骤9）

- **决定**：8 个分维度模块的「取哪些分组、怎么标记、点了要筛什么」集中在
  `src/features/dimensions/dimensionViews.ts`（纯函数 + 单测），组件只负责渲染：
  - `drilldownValueOf`：`topNWithOther` 生成的**合并行**（`其他（N 个分组合并）`）返回 `null`，
    界面因此不给「只看该组」按钮——合并行不是一个真实维度取值；
  - `scatterPointsOf`：**同时排除**合并行与分母 0 的分组。分母 0 画上去会变成「拒率 0%」的假点，
    合并行会在图上冒充一个岗位 / 序列值；但两者**都继续留在下方数据表里**（合计数不能丢）；
  - `sampleTagOf`：样本门槛统一取引擎的 `sampleSufficiencyOf`（默认 D ≥ 10），组件不自己比 10；
  - `moduleUnavailableReason`：被数据集禁用的模块必须显示原因，且原因缺失时也给一句可读文案。
- **理由**：这三类规则横跨 8 个 section，一旦在组件里各写一遍，就会出现
  「表里能点的合并行在图上也能点 / 图上有 12 个点而表里只有 8 组」这类自相矛盾；
  放进纯函数层才能被单测钉住（`dimensionViews.test.ts` 13 例）。
- **影响**：新增维度或新增 section 时，下钻维度必须由该表**自己**声明
  （学校表下钻 `'school'`、GPT 表下钻 `'isGptSchool'`、房补表下钻 `'housingType'`），
  不得复用别的表的维度参数；散点只能在调用方给定的分组集合上生成，不得在图里再过滤数值。

## D-043 分维度分析随看板同页渲染，共用同一份筛选快照（步骤9）

- **决定**：`DimensionAnalysisPanel` 直接挂在 `DashboardWorkspace` 内

- **理由**：PRD 8 章与 AGENTS §4 都要求「复用统一筛选、引擎和图表组件，禁止独立口径」。

## D-044 被禁用的模块不得照旧出金额；房补金额分位与薪资同一道闸门（步骤9）

- **决定**：`CompensationSection` 接收看板传入的 `comparable`（= `dataset.metadata.salary.comparable`），
  用它**同时**闸住两处金额分位：薪资分布（`salaryDistributionByUnit`，引擎自带 `comparable` 选项）
  与**现金房补金额分位**（`housing.cashByPeriod` 的 P25/P50/P75）。未确认币种 / 计薪周期时，
  后者不再渲染分位表，而是一句禁用说明。
- **理由**：质量层的 `SALARY_UNIT_UNCONFIRMED` 一次性禁用**两个**模块
  （`quality.ts` 的 `['薪资对比','房补对比']`），因为现金房补本身就是按计薪周期计的金额，
  与薪资同一口径问题。此前界面会出现自相矛盾：章节提示写着「房补对比已被标记为不可用」，
  下面却照旧列出 P25/P50/P75 金额——等于把没有可比口径的数字当结论给出去。
- **影响**：房补的**类型分布与各率**（`housing.groups`，来自通用分组聚合）**不受影响**、仍然显示，
  因为它不含金额；只有金额类派生值需要闸门。以后新增任何「金额 / 周期 / 分位」类展示，
  都必须先接这道 `comparable` 闸门，不得只在 `SectionShell` 的提示里写一句「已禁用」了事。
  配套约定：`HistogramChart` 的同数数据表必须真的存在（分箱标签与计数作为文本渲染），
  否则图表的 `aria-label` 不得声称「同数数据表见下方」。

## D-053 规则版本 = 语义基线 + **配置摘要**；改名单必须换版本（步骤12）

- **决定**：新增 `domain/configVersion.ts`，把**影响清洗结果**的配置
  （`gptListMode` / `gptListComplete` / `gptList` / `schoolAliases` / `dedupStrategy` /
  `includeHiddenRows` / `dropHeaderEchoRows`）规范化后压成 8 位摘要，
  写入 `RuleVersion.configRevision`（新增可选字段），由 `cleanSheet` 在数据集元信息里落盘。
  摘要算法只有一处实现（`buildConfigRevision`），界面只调用不算。
- **理由**：`RULES_VERSION` 是**语义基线**，只在规则实现变化时才动，它无法表达「用户改了名单」。
  于是会出现一个说不清的状态：两次分析用的是**不同的名单**，数据集与报告上的 `rulesVersion`
  却一模一样，报告无法回溯到底按哪套配置算的（PRD 4.2 要求结论可回溯到「当时用的是哪套规则」）。
- **影响**：改名单 / 别名 / 去重策略会换版本，因此「变更名单先展示影响并生成新版本」这条验收可核对。
  摘要只取与结果有关的字段，且先做**规范化**（名单去空白去重排序、别名按 `别名=>标准名` 排序），
  所以「同一批学校用不同顺序粘贴」不会产生两个版本——那只是录入顺序差异，不是规则变化。
  新增影响结果的设置项时**必须**显式加入 `CONFIG_REVISION_FIELDS` 并补测试，不得靠默认。

## D-054 数据集必须保存**完整设置快照**，不能只存摘要与几个散字段（步骤12）

- **决定**：`DatasetMetadata` 新增可选字段 `cleaningSettings`，
  由 `cleanSheet` 在提交那一刻存入当次使用的**完整** `CleaningSettings`。
- **理由**：`configRevision` 只能回答「两次分析是不是同一套配置」，
  **不能回答「当时到底用的是哪套配置」**。元数据原本只冗余了 `dedupStrategy` / `salary` /
  `dataAsOf` / `importMode`，`gptList` / `gptListMode` / `gptListComplete` / `schoolAliases` /
  `includeHiddenRows` / `dropHeaderEchoRows` 全部丢失，导致界面无法把「当前草稿」与
  「已提交设置」做差、也就无法在改动前展示影响（PRD 10.5）。
- **影响**：变更影响预览直接从 `dataset.metadata.cleaningSettings` 取基准，
  **不允许**再由某个组件的 `useState` 记住一份——组件状态只活在这一次访问里，
  用户离开清洗页再回来就丢了，而「旧报告按哪套设置算的」必须随数据集长期可查。
  旧数据集（步骤12 之前产生）没有该字段，调用方按「无法比较」处理，
  **不得**据缺失就假设「设置没变」。

## D-055 跨标签页失效是**推送式**的；补发 `locked(tab)` 让既有解释真正可达（步骤12）

- **决定**：`storage/db.ts` 的 `onConnectionLost` 在原有 `connection-closed` 之外，
  再广播一次 `{ type: 'locked', reason: 'tab' }`。
- **理由**：审计时发现 `VaultLockReason` 里的 `'tab'` 是一个**死枚举值**——
  全仓库从未发出过，因此 `vaultText.describeLockReason('tab')` 那句面向用户的解释
  （「其他标签页修改了本地仓，本页的解锁状态已失效」）**从来没有机会显示**。
  但失效本身是即时发生的：IndexedDB 的 `versionchange` 就是浏览器对同源其他连接的**主动推送**，
  `db.ts` 收到后会立刻 `db.close()` + `dropVaultKeys()`。
  也就是说机制是对的、解释是可达不了的——用户会遇到「数据没了但界面不说为什么」。
- **影响**：同时修正了两处此前**写错前提**的说明（`features/settings/storageBoundary.ts` 与
  `features/privacy/privacyText.ts` 原写「其他标签页不会即时推送，靠下一次读写才发现」）。
  现在统一表述为：**推送负责让界面立刻解释，写入前的版本校验负责兜住推送被丢掉的情况**，
  两道互补保险。这也纠正了步骤12 收尾时子代理的一条错误判断
  （它把「`vaultEvents` 是同页模块级 `Set`，不跨标签页」错误地外推成「跨标签页不会即时通知」；
  前者成立，后者不成立）。

## D-056 `vite.config.ts` 必须忽略 vitest 的临时目录，否则 `npm run dev` 会被打死（步骤12）

- **决定**：`server.watch.ignored` 增加 `/(^|[\\/])\.[^\\/]*\.tmpdir([\\/]|$)/`
  （同时显式保留 `**/node_modules/**` 与 `**/.git/**`）。
- **理由**：vitest 会在**被测试文件旁边**建形如
  `.PrivacyPage.test.tsx.<pid>.<hash>.tmpdir/` 的临时目录（项目根目录也会有一个
  `.vite.config.ts.*.tmpdir/`），而 Vite 的 watcher 默认只忽略 `node_modules` 与 `.git`，
  于是它会去 watch 这个转瞬即逝的目录；在 Windows 上文件被删掉 / 占用时 `fs.watch` 抛 `EBUSY`，
  该错误**未被捕获**，会直接把 `npm run dev` 进程打死。
- **影响**：本项目**实际发生过一次**（用户正在用 demo 时 dev server 挂掉，stderr 里是
  `UVException` + `EBUSY`）。修复后按同一条件复现验证：在 dev server 运行期间跑完整
  `npx vitest run`（905 例），服务保持 HTTP 200 存活，日志无 EBUSY。
  用正则而不是 glob，是因为 chokidar 各版本对 glob 的处理有差异，而这里只需匹配
  「以点开头、以 `.tmpdir` 结尾」的目录名。

## D-048 导出只有一个数据来源：唯一 `SanitizedReport`，三种格式不得各自读报告对象（步骤11）

- **决定**：新增 `src/privacy/`（纯函数）出 `SanitizedReport`，新增 `src/exporters/` 出四种格式。
  其中 `exporters/sections.ts` 的 `reportToSections(report)` 是**唯一取值层**：
  XLSX / Markdown / 打印 HTML 都只把「章节 → 表 → 行列」排版成自己的格式，
  **不允许**任何一个 exporter 直接去读 `report.kpis` / `report.dimensions`。
- **理由**：PRD 11.2 要求三种格式「同一筛选、同一数据版本、同一口径」。
  若每种格式各自遍历报告对象，只要有一处漏读 `suppressed` 或把 `null` 当成 0，
  同一个数字在三种文件里就会不一致——而这类不一致极难在验收时发现（要开三个文件逐个比对）。
  把取值收成一层，口径差异在结构上就不可能发生。
- **影响**：新增格式（例如以后的 CSV）只需写排版，不得再写一遍取值；缺失与抑制一律渲染成 `—`，
  绝不用 0 或 0% 占位。修口径时改 `sections.ts` 一处即可。

## D-049 互补抑制在**合并之后**做，且数学上做不到时整维抑制（步骤11）

- **决定**：`applyComplementarySuppression(groups, { minSuppressed: 2, suppressBelow })` 只负责
  「在已有抑制的基础上把本维度被抑制组补到至少 2 个」；主抑制（`n < 门槛`）由调用方在此之前完成。
  调用顺序固定为**先合并小组、再做互补抑制**。若本维度只有一个分组、或可补充的候选不足，
  该函数**不硬补**，由 `buildSanitizedReport` 把**整个维度**抑制并写明原因。
- **理由**：这是 PRD 10.6「避免用总计减去其他组还原小组」的落点。只抑制一个组时，
  读者用「总计 − 其余组」可以精确还原它，抑制等于没做。而在后补一个组时，
  必须先合并——被合并掉的分组已经不显示标签，再算一次「已被抑制」会把它重复计入门槛。
  数学上做不到「至少两个」时硬标一个更糟：它会让读者以为互补抑制生效了，实际仍可反推；
  整维抑制并说明原因才是诚实的做法。
- **影响**：抑制说明（`SuppressionNote`）必须能对照 `suppressedGroupCount` 复核，
  且**只统计互补抑制新增的部分**，不把主抑制已合并掉的组重复计数。

## D-050 数字型哨兵不参与值匹配；准确薪资由**结构**消除而不是靠检索（步骤11）

- **决定**：`findSensitiveFields` 的**值**匹配只针对字符串哨兵（候选人 / HR / 推荐人姓名、
  需求 ID、原因原文等）；数值型哨兵（如 `3500`）不参与子串匹配。
  准确薪资的风险改由**结构**消除：报告里任何金额都只以 `SalaryBand` 区间出现
  （`quantileMode: 'band'` 时精确实数为 `null`、只留区间；`'hide'` 时两者都为空）。
  字段名闸门按**键名**判定（`dimension: 'recruiter'` 只是维度名，不是 HR 姓名列）。
- **理由**：数值子串匹配会产生无法消除的误报——报告里合法的计数 `6` 会命中金额 `3500`
  的某个数字片段，把正确报告拦死；为了绕过误报而放宽匹配，又会漏掉真正的泄漏。
  既然薪资已经不可能以准确值出现在模型里，用结构保证比用检索兜底更可靠。
- **影响**：新增任何金额类字段时**必须**先过 `salaryBandOf` 之类的分桶，
  不得因为它「只是一个数字」就写进报告；哨兵检索仍然保留，作为最后一道兜底而不是唯一防线。

## D-051 首屏包已到 576.52 kB：路由级 `lazy()` 是独立的一步，不在步骤11 顺手做（步骤11）

- **决定**：本步把四种导出格式的重依赖都留在**动态 import 的另一侧**
  （`xlsx` 492.37 kB 懒 chunk、`echartsRegister` 542.96 kB 懒 chunk、`png` 2.44 kB 懒 chunk），
  构建产物核对首屏包里 SheetJS 内部符号（`write_zip` / `CFB` / `SSF` / `SheetNames`）与
  ECharts 内部符号（`zrender` / `BarChart` / `AriaComponent`）**均为 0 次**。
  但首屏 `index-*.js` 从步骤9 的 494.12 kB 增长到 **576.52 kB**，本步没有顺手改成路由级懒加载。
- **理由**：`App.tsx` 现在是**全静态 import 所有页面**，所以每个页面新增的界面代码都会进主 chunk；
  导出页实测约 +52 kB。改成 `React.lazy()` 是**路由层**的结构改动，会影响全部 9 个页面、
  空态首帧与错误边界，属于独立一步的收益与风险，不适合塞进一次导出功能的收尾里。
- **影响**：这是**已知且已记录**的技术债，不是遗漏。要做时应当单独一步：
  按路由切 chunk + 给每个懒页面一个与现有空态口径一致的 fallback + 复测
  「首屏不含 ECharts / 不含 SheetJS / 不含 Dexie」三条不变量。在那之前，
  新增页面代码都会继续推高主 chunk，评审时应按同一口径记录增量。

## D-052 PNG 用注入式渲染器，真实像素在 Node 里明确未验证（步骤11）

- **决定**：`exporters/png.ts` 的 `renderChartPng` 接受注入的 `CanvasFactory` /
  `OffscreenChartRenderer`，在 Node 测试里只验证
  「report → chart spec → option → 渲染器 → data URL → 字节」这条链路与 DPI 尺寸换算；
  真正的 ECharts 离屏渲染走 `charts/echartsRegister.ts` 新增的 `renderOffscreenChart`，

  `exporters/index.ts` **刻意不导出** `png.ts`，否则 ECharts 会被静态拉进首屏包。
- **理由**：AGENTS §5 要求「未执行的平台明确写未验证」。Node 没有 canvas 光栅化，

## D-045 拒 offer 原因只查表不推断；「未分类」与「未填写」必须分开（步骤10）

- **决定**：新增 `domain/analytics/rejection.ts` 的 `classifyRejectionReason`：对附件里
  `拒绝原因` 一列的取值做**精确**字典查表（去掉全部空白后比对，拉丁字母忽略大小写），
  词典只收录 PRD 9.2 的十个类别名与附件 / 口语里确实出现过的等价写法。
  匹配不上的一律落到 **`未分类`**，并与 **`未填写`** 分开计数、分开展示；
  `未分类` 还单列原值样例（去重 + 截断）供人维护字典。
- **理由**：PRD 9.2 要求「不凭候选人背景推断原因」，AGENTS §6 也禁止把自由文本当结论。
  一旦用子串匹配，「薪酬太低所以去了别家」会同时命中「薪酬」和「其他 offer」——
  猜哪个都是错的。把「未分类」显式暴露出来，才能把「字典不够用」这件事变成待办，
  而不是悄悄变成一个看起来有依据的饼图。「未填写」与「未分类」的处置也不同：
  前者要补访谈，后者要补字典。
- **影响**：原因分布的分母**恒为 R**（含「未填写」），所以原因全空时填写率是 **0%**（不是 null），
  且绝不允许据此输出「主要因为薪酬」。新增原因类别只能改这份字典并补测试，
  **不得**在组件里写 `includes` / 正则去猜。

## D-046 未知条件 ≠ 不满足；结论只在三条门槛同时满足时成立（步骤10）

- **决定**：`evaluateCondition` 的基础条件（GPT、无补贴、低于同岗 P50、等待超阈值）返回三值
  `boolean | null`，`null` 表示**未知**。规则命中要求**所有**条件都 `=== true`；
  任何条件为未知的记录既不进命中数、也不当不满足，而是在 `unknownConditions` 里逐条列出
  （含 `detail` 说明为什么是未知）。结论分三级：`insufficient`（D < 10 或 R < 3）→
  `description`（够样本但率差 < 10 个百分点）→ `observed`（三条同时满足）；
  只有 `observed` 才允许出现「观察到…关联」的措辞。
- **理由**：把未知当不满足会系统性**低估**风险条件（数据缺得越多看起来越安全）；
  把未知当满足则会凭空造出风险。两者都是错误结论，所以必须三值。
  时间条件尤其危险：附件没有拒绝日期，`waitingDurationFor` 对拒 offer 记录恒返回
  `kind: 'unknown'`，因此任何含「等待超阈值」的组合规则在拒 offer 人群上**永远无法命中**——
  这是正确行为（如实显示为未知条件），不是 bug。
- **影响**：`insufficient` 一律只描述、不排名；率差是「命中组率 − 当前筛选整体率」，
  两侧任一分母为 0 时率为 `null`、率差也为 `null`（不显示 0 个百分点）。
  阈值三项与 `waitingThresholdDays` 都是**运营配置**、随结论返回并需随报告记录，
  不是行业标准。结论文案里禁止出现概率、因果与「不招某类学校」类建议（有测试钉住）。

## D-047 拒 offer 专项的结论层放在 `src/insights`，与 `domain/analytics` 分工（步骤10）

- **决定**：`domain/analytics/rejection.ts` 只出**计数与率**（分组、原因分布、条件判定、规则评估），
  `src/insights/rejection.ts` 出**结论**（`buildRejectionInsight` 组装两个人群、各维度对比、
  规则评估与行动建议）。界面只 `import ... from '../insights'`。
- **理由**：AGENTS §4 把 `insights/` 定义为「本地确定性结论与规则化行动建议」，
  而 §2.3 要求指标只实现一次。把「率」留在 domain 让看板与报告都能复用，
  把「结论」上移到 insights 让规则、阈值与免责声明集中一处，组件就不可能各写一套阈值。
- **影响**：`GroupSummary` 新增 `groupComposition`（拒 offer 组 / 入职组的人数），
  由 `summarizeRecords` **一次遍历**算出，因此「组内构成」与「特征内率」来自同一个汇总对象，
  不会出现两处口径漂移。组内构成是**画像构成**（该取值在拒 offer 组的人数 ÷ R），
  与被下钻特征的拒 offer 率不是同一个东西，界面的列名与说明必须写清楚这一点。

## D-057 AI 载荷用**白名单重建**，不用「复制后删字段」（AI-1）

- **决定**：新增 `privacy/aiSummary.ts` 作为 `SanitizedAiPayload`（`ai-summary/1`）的**唯一**定义与
  构造点。载荷由固定字段逐项构造，只从允许的来源取值；`AI_SUMMARY_KEYS` 是键白名单，
  `checkSanitizedAiPayload` 在发送前做「出现任何未知键即失败」的运行时校验。
- **理由**：「删字段」的安全性取决于有没有想到该删的键——往聚合结果里加一个字段就会静默泄漏；
  「白名单重建」的安全性取决于有没有显式允许——新增字段**默认进不去**。两种失效模式不同。
- **影响**：`aiPayload.ts` 只保留历史 v1 结构与其校验器（`isLegacyAiPayloadV1`），
  避免两个同名 `SanitizedAiPayload` 同时导出。
  `SanitizedAiPayload.schemaVersion` 刻意是**字面量类型**而不是 `string`：
  否则 `SanitizedReport`（两者都有 `schemaVersion` / `generatedAt` / `quality` 等键）
  会**结构上可赋值**给载荷，「把本地报告当 AI 载荷传进去」在类型层面就能通过。
  收尾时正是因为写成 `string` 而让 `report.test.ts` 的编译期断言失败，改回字面量后恢复不兼容。

## D-058 身份禁出加一道**取值形状**闸门，不只靠维度名（AI-1）

- **决定**：`safeKeyOf` 的最后一道判断是 `looksLikeIdentifier(cell.key)`——
  取值以 ASCII 字母数字开头，且**含** `-` / `_` 或长度 ≥ 12 时，整格不发。
- **理由**：AI05 要求载荷里没有需求 ID，而标准表里就有一列「需求ID」，取值形如 `REQ-0001`。
  这类值可能被填进**任何**一列，逐维度列举必然漏。
  这道闸门是**验收测试逼出来的**：最初的正则 `^[A-Za-z0-9][A-Za-z0-9_-]{3,}$` 只认 ASCII，
  于是 `REQ-合成-9901`（含中文的需求 ID）**整串漏过**，被 AI05 测试当场抓住。
- **影响**：阈值刻意**不**把「短的纯字母数字」当 ID，否则会误伤 `Boss`、`HR推` 这类受控枚举取值
  （渠道就叫 Boss），把正常功能整维丢掉。宁可少发一格并计入抑制数，也不赌「这列不会是 ID」。

## D-059 来源维度名必须归一化，否则会**静默丢功能**（AI-1）

- **决定**：`canonicalDimensionOf` 把来源字段名映射到载荷粒度名（`school` → `schoolLevel`、
  `position` → `positionCategory`），且 `recruiter` 必须进白名单。
- **理由**：来源系统给的是记录字段名，载荷白名单用的是能对外说的粒度名。不归一化时
  `school` / `position` 会被判成「当前隐私级别不发送该维度」，`recruiter` 干脆不在白名单里——
  三者**全部静默消失**。这也是验收测试逼出来的：AI05/AI08 的断言发现 HR、学校、岗位三类
  `dimensions` 全空，才暴露该 bug。危险之处在于它**看起来像「更安全」**（少发了东西），
  实际是功能坏了且没有任何提示。
- **影响**：`AI_DIMENSIONS_BY_LEVEL` 的 standard/custom 增加 `recruiter`，`AI_DIMENSION_LABELS` 同步。
  以后新增维度必须同时改三处（白名单、别名、标签）并补测试。

## D-060 预览 hash 覆盖「一切会影响实际请求的输入」，一次性令牌绑定 hash（AI-1）

- **决定**：`aiPreview.ts` 的 `buildAiPreview` 产出完整预览与稳定 `hash`；
  `confirmPreview` / `consumeConfirmation` 做一次性确认。hash 输入显式包含
  schema 版本、提示词版本、载荷 JSON 全文、messages 全文、模型与全部参数、端点；
  **不含** `generatedAt`。
- **理由**：① 少算任何一项都会造出「内容变了但 hash 没变」的漏洞，等于让旧确认对新内容生效
  （AI03/AI09）；② `generatedAt` 只是展示时间，算进去会让同一份内容每次生成都得到不同 hash，
  反而无法判断「内容是否真的变了」；③ 布尔量 `confirmed` 无法表达「确认的是哪一份内容」，
  令牌绑定 hash 才能让「改了参数 → 旧确认失效」在结构上成立，不依赖界面有没有记得重置状态
  （AI02 防双击同理）。
- **影响**：预览的 `payloadJson` 序列化一次后被预览展示与发送**共用**
  （两处各自 `JSON.stringify` 是「预览与实际发送不一致」的经典来源）。
  预览逐字渲染进界面，因此**提示词里也不许出现 Markdown 强调标记**：
  收尾时改掉 user 提示词里的 `**聚合脱敏摘要**`，并把 `AI_PROMPT_VERSION` 由
  `ai-prompt/1` 升到 `ai-prompt/2`（改文案必须升版本，否则「hash 没变但提示词变了」，历史无法回溯）。

## D-061 `quality.missingSalary` 必须由引擎反推，不许硬编码 0（AI-1）

- **决定**：`missingSalaryCount(总记录数, 可用薪资样本数)` = `max(0, 总数 − 可用数)`，
  可用数取 `metricAvailability` 里「薪资对比」条目的 `validSampleCount`
  （`cleaning/report.ts` 的 `sampleCountFor` 已定义它就是「薪资金额非空的记录数」）。
- **理由**：AI 界面最初把它硬编码成 `0`（理由是「引擎没暴露该派生计数，组件不许自己数」）。
  那个理由对约束的理解是对的，但结论错：`0` 会被读成「没有记录缺薪资」，
  而它是一个**会随载荷一起出现在预览与请求里**的数字——假数据比缺失更糟。
  用一次减法复用既有口径，既不新造指标，也不说谎。
- **影响**：`validSampleCount` 为 `null`（模块口径不适用）时按「全部记录的薪资都不可用」计，
  **不用 0 冒充**。以后新增载荷里的质量计数，一律先找引擎里已有的口径反推；
  找不到就在引擎里补，不得在组件里就地填一个「看起来无害」的常量。


## D-062 `AnalysisSummary` 是唯一的本地 → AI 交接契约，装配逻辑必须离开组件（AI-2）

- **决定**：新增 `src/ai/summary.ts` 的 `buildAnalysisSummary(input)` 纯函数，
  输入已算好的分析结果、输出一份 `AnalysisSummary`（frozen / scope / kpi / dimensions /
  cycleBandGroups / rejection / cycle / quality / caliberNotes / 体积与调整记录）。
  `DashboardWorkspace` 里原先手拼 AI 输入的那 70 行装配代码**全部删除**，改为调用它。
- **理由**：AI-1 交付时 `AnalysisSummary` 生成器还没做，于是看板组件里堆了一段装配代码
  （手列 13 个维度、拼 `scope`、反推缺失薪资）。那段代码有三个问题：**不可测**
  （口径只能靠渲染冒烟）、**会漂移**（看板改口径没人会记得同步改它）、
  **与 PRD 16.2 的「冻结快照」语义不符**（组件内的 `useMemo` 不是一份可传阅的契约）。
- **影响**：`AnalysisSummary` 刻意**没有** `records` 字段，让「摘要里出现原始行」
  变成类型错误而不是代码审查问题。但 `dimensions[].summaries` 按 `GroupSummary` 契约
  带着 `records`——它是**本机专用**字段（只给候选格换算层读 `groupComposition` 与 `cycles`），
  **不得**写进载荷、历史或日志；外发边界仍由 `privacy/aiSummary.ts` 的白名单重建负责。

## D-063 组间构成与特征内率写在**同一行**，不做同维度双表（AI-2）

- **决定**：拒 offer 组内构成（`rejectedGroupCount` / `joinedGroupCount`）作为
  `AiPayloadRow` 的可选字段，与 N/D/R **同一行**输出；载荷里只有一个
  `rejectionComparison` 说明块（两个人群的分母与说明），**不再有第二张同维度的表**。
- **理由**：最初的设计是「每维两张表：一张特征内率（N/D/R）、一张组内构成」。
  这个设计**被否决**了，因为两张表在同一维度上按 key 对齐后能反算出不在比较人群里的量——
  该组的 D 与 R 已知、组内构成已知，两者相减就得到剩下的部分。
  PRD 16.3 明确要求「同一请求中的总体、城市、HR、交叉表一起检查，
  **不能每张表各自过关后拼接**」。
- **影响**：`privacy/aiSummary.ts` 里刻意**不再定义**那个被否决的表类型——
  留着定义，下一个人就会顺手把它加回来；类型不存在，这条路才是关着的。
  组内构成的样本量闸门用的是**比较人群**（`拒 offer 组 + 入职组 ≥ 5`）而不是 `D`：
  用 D 判断会让「D 够大但组间只有 3 人」的行混进来，而那正是可反算出个人的情形。

## D-064 HR 代号必须由同一批分组预生成，否则组内构成会**静默消失**（AI-2）

- **决定**：新增 `buildRecruiterOrdinals(dimensions)` 先定下「原始取值 → `HR-n`」映射，
  `buildAiSourceCells` 与 `buildAiProfileCells` 两次遍历**共用**它。
- **理由**：代号原本按「每组 `groups` 的首次出现顺序」就地现编，于是主表与组间比较表
  各自从 1 开始编，同一个 HR 在两处拿到**不同代号**。而脱敏引擎是按
  「载荷维度名 + 原始取值」把组内构成合并到主表行上的——代号不一致就匹配不上，
  组内构成**静默消失**：界面看起来一切正常，只是那一列数字没了。
  这是 AI-2 自己在写测试前先发现的问题，属「看起来像更安全」的同类陷阱（对照 D-059）。
- **影响**：这一层现有两道守卫——`buildRecruiterOrdinals` 统一编号，
  以及 `profileCellOf` 在拿不到代号时**不发这一格**（而不是临时编一个对不上的代号）。

## D-065 摘要的维度表**不做 TopN 预裁**，TopN 归脱敏引擎（AI-2）

- **决定**：`tableOf` 输出该维度的**全部**分组行；「每维 Top10 + 合并其余」仍只由
  `privacy/aiSummary.ts` 的 `collapseTopN` 负责。超预算时**整表丢弃**并记进 `adjustments`，
  绝不截断行。
- **理由**：初版实现按 `slice(limit)` 在摘要侧预裁，测试立刻抓到：
  城市维度只剩 1 行（16 条），合成数据的 48 条对不上。这不只是数字错——
  引擎的 `collapseTopN` 需要**全部**行才能算出正确的「其他（N 个分组合并）」；
  预裁会让被丢掉的行既不进 Top10 也不进合并行，等于凭空少了一批记录。
- **影响**：`adjustments` 的裁剪顺序是穷尽的（最后连城市也会丢，退化为「只剩总体指标」），
  因为「留下一张装不下的表」会让 `totalBytes` 继续超预算，而超预算发出去正是 PRD 17.1 要防的事。
  另：`missingSalaryCount` 在 `src/ai/summary.ts` 与 `features/ai/aiSourceCells.ts` 各有一份实现，
  两者同口径（与 D-061 一致）；这不是遗漏，是刻意保持 `src/ai/` 不反向依赖 `features/`。

## D-066 不支持的参数**在结构上不存在**，而不是填一个会被服务端忽略的值（AI-3）

- **决定**：`AiModelParams` 的 `temperature` / `topP` / `reasoningEffort` 都是**可选**的，
  语义是「字段存在 = 会出现在请求正文里；字段缺失 = 不发送」。判定与收敛只由
  `src/ai/aiConfig.ts` 的 `resolveAiParams` 一处做，组件不得自己 clamp 或判断。
- **理由**：官方《思考模式》文档原文——「思考模式不支持 `temperature`、`presence_penalty`、
  `frequency_penalty`。请注意，为了兼容已有软件，设置参数不会报错，但也不会生效」；
  「`top_p` 仅在思考模式下生效……在非思考模式下，该参数恒为 1.0，传入的值会被忽略」。
  **「不报错但不生效」比报错更危险**：用户会以为温度真的起了作用。
  若把 `temperature` 设成必填 `number`，「思考模式下不发温度」就只能靠填一个假值表达——
  发出去被忽略，但预览里显示着一个看起来生效的数字。
- **影响**：`resolveAiParams` 的 `notices` 把每一次本地调整（收敛、回落、忽略）**逐条显示**给用户，
  不再静默处理。同理，`max_tokens` 的上界取「模型能力」与「产品预算」中更严的一条。

## D-067 AI Key 的明文只在一处，且**类型上**不给出（AI-3）

- **决定**：`src/ai/keySession.ts` 用模块级单例持有内存 Key；对外只导出
  `AiKeySnapshot`（`present` / `savedAt` / `permission`，**没有 `value` 字段**）与
  `readAiKeyForRequest()`（唯一取明文的口，名字即用途）。掩码由 `maskApiKey` 提供
  （前 3 后 4），界面只能拿掩码。
- **理由**：Key 有四处要用（设置页、看板入口、预览面板、未来的网络适配器），各自 `useState`
  必然出现「设置页删了 Key，看板还以为有」这类两份真相。更重要的是「不小心把 Key 渲染出来」
  应当是**编译错误**而不是靠代码审查发现——把 `value` 从界面可及的类型里去掉，
  这条路就是关着的。
- **影响**：`AiKeySnapshot` 的序列化结果里不含 Key（有测试钉住）；锁仓只清内存、
  **不动**加密仓里的那一份（删 Key 是独立操作）；许可按 **origin** 绑定，
  换地址即失效且不转发旧 Key。`saveAiSettings` 连「接受一个 Key」的参数都没有，
  因此「顺手把 Key 存进偏好」在类型层写不出来。

## D-068 预览 hash 必须逐字段列出参数：`JSON.stringify` 会吞掉 `undefined`（AI-3）

- **决定**：`privacy/aiPreview.ts` 的 `hashInputOf` 改为逐个列出参数键，缺失项显式写成 `null`。
- **理由**：原本是 `params: parts.params`，而 `JSON.stringify` **会丢掉值为 `undefined` 的键**。
  于是「温度从 0.7 变成**不发送**」与「温度保持 0.7」产生**同一个 hash**——
  两者是不同的请求（一个带 temperature、一个不带），却共用一个确认，
  直接违反 AI03「修改参数后旧确认失效」与 AI09。
  这个漏洞在 AI-1 时不存在（当时参数全是必填），是 AI-3 把它们改成可选**才**出现的：
  类型放宽会引入新的一类边界，必须回头检查依赖「序列化形状」的地方。
- **影响**：`AiModelParams` 任何新增的可选字段都必须同时加进 `hashInputOf`，
  否则它就是一个「改了不影响 hash」的参数。

## D-069 模型目录是**人工核实后写死的常量**，不做探活也不拉 `/models`（AI-3）

- **决定**：`src/ai/catalog.ts` 的 `AI_MODEL_CATALOG` 是版本内的常量，带核查日期
  （2026-09-26）与官方来源链接；官方已停用 / 已下线的旧模型**照原样保留**并逐条写明
  兼容风险与建议改用的模型 ID。目录里没有的 ID 按**最保守**能力处理并标 `userProvided`。
- **理由**：本项目的对外承诺是「只有用户逐次确认后才发一次请求」。若打开设置页就去查
  `/models`，这条承诺立刻破掉（AI01/AI17 都要求开关、保存 Key、看历史零请求）。
  另外「不静默替换模型」是硬要求：自动把 `deepseek-chat` 换成 `deepseek-flash`
  会改变计费与结果，属于用户不知情的变更。
- **影响**：目录需要**人工维护**——官方改价或停用模型时必须更新这张表并改核查日期
  （测试会检查 `AI_CATALOG_VERIFIED_AT` 是合法日期格式、来源是官方域名）。
  未登记的模型 ID 不假装认识它：能力按最保守处理，费用按目录最高价估算。

## D-070 出站边界从「零调用」改为「有且仅有一个适配器」，守卫跟着改口径（AI-4）

- **决定**：`src/ai/client.ts` 是全仓**唯一**允许出现网络调用形状的文件；守卫测试从
  「全仓一个都没有」改为「全仓只允许出现在 `ai/client.ts`，且该文件里确实有一次」。
  `src/features/ai/**`（直接面对用户的代码）仍然**一个都不许有**。
- **理由**：AI-1 至 AI-3 守的是「零调用」，那是一条**会因为功能推进而必然失效**的断言——
  若只是把它删掉，就同时丢掉了「组件里不许自己发请求」这条更长期、更值钱的约束。
  改成「唯一适配器」既承认了出站的存在（PRD 18.3 要求请求由唯一 adapter 发出），
  又保住了原守卫真正想防的事：**顺手在界面层加一个请求**。
  测试里还加了一条「适配器里确实有一次调用」的断言——否则「一处都没有」也会让前一条空转通过。
- **影响**：以后任何需要发请求的功能都必须经 `sendSanitizedAiRequest`。
  适配器的签名里**没有**能装下 `NormalizedRecord[]` / `RawRow` / `SanitizedReport` 的位置，
  守卫用 TypeScript scanner 剥掉注释与字符串后断言这些名字不出现在代码里
  ——「把原始记录传给网络层」在类型与测试两层都走不通。

## D-071 思考模式的三个参数按官方形状表达「不发送」，而不是填默认值（AI-4）

- **决定**：请求正文里
  `thinking` 是**对象** `{type:'enabled'|'disabled'}`，内部 `'auto'` 的语义是**不带这个字段**；
  `reasoning_effort` 只在思考模式**明确开启**时发送，且**绝不发 `none`**；
  思考模式下不发 `temperature`；`top_p` 只在思考模式明确开启时发送。
- **理由**（均据 2026-09-26 核实的官方《Chat Completions API》）：
  官方 `thinking` 的默认值就是 `enabled`，所以「替用户写上 `enabled`」与「不写」虽然结果相同，
  但**正文会与用户批准过的预览不一致**——而 AI-1 的全部设计都建立在「预览即正文」之上；
  `reasoning_effort` 的 `none` 也表示关闭思考模式，与 `thinking.type='disabled'` 重复表达同一件事，
  两个字段同时出现时谁优先官方没说，因此**不用**它；
  `temperature` 在思考模式下「不报错也不生效」（D-066 已定的口径）。
- **影响**：`'auto'` 这一档必须一路传到正文构造层，中途任何「顺手补个默认值」都会破坏
  「预览与正文逐字节一致」。`aiRequest.test.ts` 逐条钉住这四种组合。

## D-072 错误分类在两层 try/catch 之间必须**透传**，不能被兜底压平（AI-4）

- **决定**：新增 `isAiRequestError`，适配器的 `normalizeFailure` 在兜底之前**先认**它，
  是 `AiRequestError` 就原样返回。
- **理由**：HTTP 非 2xx 是在适配器**内层**抛出的、已经分类好的错误（带 `status` 与官方 `error.code`）。
  内层的兜底若不先认它，就会把 `401` 重新包成 `kind:'network'`，于是 `auth` / `balance` /
  `rate-limit` 全部退化成「网络失败」，界面也就给不出「请替换 Key」「余额需你自行处理」
  这些**由分类决定**的正确建议（PRD 18.4 的表格逐行规定了不同动作）。
  这个 bug 是 AI-4 那组「8 个状态码 → 分类」的逐条测试抓出来的：
  当时 6 种分类断言全挂，而失败信息显示的是「网络失败」——说明错误在传递途中被改写了一次。
- **影响**：以后在调用链上再加一层 catch，必须同样先判「这是不是已经分类好的错误」。
  分类信息被压平属于**静默降级**：功能看起来正常，只是提示变得没用。

## D-073 迟到响应靠**世代号**作废，不能只靠 abort（AI-4）

- **决定**：`abortInFlightAiRequest()` 做两件事——中止在途请求、**并推进一个单调递增的世代号**；
  `sendAiRequestOnce` 返回的 `current` 表示「结果是否仍属发起时的世代」，
  为 `false` 时调用方**必须丢弃**。
- **理由**：`AbortController.abort()` 是**异步**生效的。只清一个「已取消」布尔量会留下窗口：
  先 abort、后响应已经解析完成、响应把结果写进界面。世代号让迟到响应在**比较时**作废，
  与 abort 的时序无关；测试里正是「abort 之后仍手动结算响应」来复现这个场景的。
  PRD 16.2 要求「锁仓 / 切换数据集 / 清除历史时中止在途请求并提升任务版本，
  迟到响应不得重新写入」——「提升任务版本」就是世代号。
- **影响**：界面必须显式处理 `current === false`（显示「这次响应已作废」），
  而不是把它当成功结果展示。取消与超时都明说「**可能已产生费用**、不承诺免收费」。

## D-074 回复侧敏感检查必须查**文本本身**，不能只查对象的键（AI-5）

- **决定**：新增 `privacy/sanitize.ts` 的 `forbiddenNamesIn(text)`（与 `containsForbiddenField`
  共用同一张由 `FORBIDDEN_FIELD_NAMES` 派生的判定表），并在 `aiResponseCheck.ts` 里
  对模型回复**文本**再判一次；`scanSensitiveFields` 的结果与它合并后去重排序。
- **理由**：初版直接调用步骤11 的 `scanSensitiveFields`，但那个函数是给**对象**用的——
  它只检查**键名**，字符串值只参与哨兵匹配、不参与禁名匹配（`SanitizedReport` 正是那种形状，
  风险也确实在键名上）。而模型回复是一整段**自由文本**：没有键可言，禁名就藏在正文里。
  于是一个本该被抓住的情况——「回复里写到了 `candidateName`」——被**静默放过**。
  这类漏检特别危险：检查显示「没有发现」，用户会以为检查过了。
- **影响**：两个检查都要跑，因为它们防的是**不同形状**的输入；
  界面上仍然只列字段名、不回显命中值（检查结果自己回显敏感值，就等于检查成了泄漏渠道）。
  这个 bug 是 AI-5 那条「回复里出现 candidateName 时应阻断导出」的测试抓出来的。

## D-075 历史的身份就是加密仓那一行的主键，载荷里不放 `id`（AI-5）

- **决定**：新增 `vault.appendVaultObject`（每次生成新 id、绝不覆盖），
  `AiHistoryPayload` **刻意不含 `id`**；读回时由 `loadAiHistory` 把**仓的行键**作为 `id`
  交给界面，删除也按同一个键执行。
- **理由**：初版让调用方传 `id` 进载荷，而删除是按仓里那一行的主键执行的——两者一旦不一致，
  表现就是「点了删除没反应」。更糟的是这种不一致**不会报错**：界面照常渲染，
  只是删除静默失败。让身份只有一处来源（仓的行键），这类 bug 就不可能发生。
- **影响**：`saveVaultObject` 是**覆盖**语义（传同一个 id 会覆盖），
  把它用于「只增不改」的列表，等于把「id 唯一」的责任推给界面层——那是最不该依赖它的地方。
  因此把「生成唯一 id + 不覆盖」变成仓的能力（`appendObject`）。
  这也是 AI-5 的测试（`删单条只删那一条`）抓出来的。

## D-076 安全 Markdown **自己写解析器**，不引第三方渲染库（AI-5）

- **决定**：新增 `src/ai/aiMarkdown.ts`（纯函数，产出只含白名单节点的树）
  与 `features/ai/AiMarkdownView.tsx`（把树映射成 React 元素）。不引入任何 Markdown 依赖。
- **理由**：三条都是硬的。① 多数 Markdown 库**默认允许原始 HTML**（或需要一个插件才关掉），
  而本项目禁止 `dangerouslySetInnerHTML`（AGENTS.md §6）——引入一个「配错一个选项就出事」的
  依赖，成本高于自己写一个只认白名单子集的解析器；② 解析结果必须是**结构**而不是 HTML 字符串，
  才能让 React 负责转义，从而**不存在「忘记转义」这条失败路径**；
  ③ 必须能**穷举**「什么不会发生」：树里没有 `html` / `image` / `iframe` / `link` 节点类型，
  所以「模型写 `<img src=...>` 会不会发请求」这个问题在**类型层**就有答案。
- **影响**：解析器只支持渲染模型输出真正会用到的那一小撮语法；遇到表格等不支持的结构
  **按纯文本显示并记录降级**（不静默改写、也不假装渲染成功）。
  链接降级成 `文字（地址）`、图片降级成 `[图片：alt]` 且**不保留地址**——
  这两条是 AI12 的核心，谁把它们改宽，`aiMarkdown.test.ts` 会失败。

## D-077 本地规则必须被「确认一次」，判据是**指纹**而不是布尔量（AI-6）

- **决定**：新增 `src/ai/subjectRules.ts`。摘要里三类取值——岗位类别（岗位类别映射）、
  学校层次（本地 GPT 名单 + 别名）、拒 offer 原因主题（原因字典）——都是**本地解释的结论**
  而不是客观事实。设置页把它们逐条摊开（会发出什么 / 永远不会发出什么 / 来自哪里），
  用户点一次「确认这批规则」；确认记录里带一个**规则指纹**，
  判据只有一条：保存的指纹等于当前规则算出的指纹。指纹覆盖配置摘要（因此换名单 / 改别名
  必然换指纹）、岗位类别映射、学校名单模式与完整性、别名条数、原因字典的类别清单。
- **理由**：用一个布尔量表达「我同意过」会有两种事故：用户不知道自己的名单 / 字典也参与了外发；
  用户改了名单之后，上一次的同意被**自动沿用**到一套新规则上。指纹把「同意的是哪一份规则」
  变成可比较的值，不依赖界面记得重置状态（与预览 hash 同一套思路，见 D-068）。
- **影响**：未确认时**仍然可以生成并逐字核对预览**（看预览不发任何东西），
  但看板拒绝发送（`canConfirm` 与 `handleSubmit` 两处用同一判据）。这条闸门是**加法**：
  `subjectRulesConfirmed` 缺省 `true`，因此既有调用方与组件测试的行为不变。
  岗位类别映射从脱敏层实现而不是界面层：把岗位全名换成类别**就是**脱敏动作本身，
  放到界面层会出现「设置页说发了 A、载荷里其实是 B」（口径只实现一次）。

## D-078 代理只定义**显式配置边界**：严格校验 + 逐条确认 + 改地址先撤销（AI-6）

- **决定**：新增 `src/ai/aiProxy.ts`（纯函数）与 `features/settings/AiProxyPanel.tsx`。
  ① 地址校验严格且**规范化**（只接受 `https:`，唯一例外是回环 `localhost` / `127.0.0.1`
  的 `http:`；拒绝凭据 / 路径 / 查询串 / 片段；路径固定 `/chat/completions`）；
  ② 登记必须逐条勾选三条风险确认后才可保存，未勾完按钮禁用；
  ③ 改地址时**先**调 `revokeAiKeyPermissionIfOriginChanged` 撤销旧许可，**再**保存新地址；
  ④ 说明文字写明「本仓库不提供代理程序」「不由网站运营方托管」「CSP 不放开任意域」。
- **理由**：代理是「请求的接收方」，能看到 `Authorization` 头里的 Key 与脱敏摘要原文——
  它比官方端点更危险，因此不能做成一个随手能填的输入框。规范化地址是必需的：
  不折叠大小写 / 末尾斜杠 / 默认端口，`https://Proxy.Example.com/` 与
  `https://proxy.example.com` 会被当成两个地址，「改地址要撤销授权」就被排版差异绕过了。
- **影响**：撤销**只清许可、不动 Key**（改个端点不该变成破坏性操作，与「关闭 AI 不删 Key」同口径）。
  登记的地址**不会被静默使用**：它只是当前目的地，仍然只在用户逐次确认的那一次请求里生效，
  且没有探活 / 预检试连。不配置代理时全部本地功能完全可用。
  本步**不放宽任何 CSP**：真正把请求发往自建代理需要用户自己构建并调整 `connect-src`
  （步骤13 落实本地版 / 含 AI 版的两套策略）。

## D-079 隐私页的三处「曾经是真话」必须随实现一起改（AI-6）

- **决定**：把隐私页里随 AI 支路推进而变成**假话**的三处改掉：
  ① 「当前版本没有任何网络请求代码 / 计算过程不产生任何出站请求」→
  改为「默认模式（AI 关闭）不出站」，并**明确写出不承诺「所有模式下绝不出站」**；
  ② 「发出请求尚未实现（AI-4 之前）」→ 改为「一次确认后的真实调用已交付」，
  同时把「浏览器直连（CORS）」标为**未验证**、不写成可用；
  ③ 「已调用 DeepSeek（当前版本尚未交付该功能）」→ 改为按现状说明
  「清除只能删本地记录，无法撤回已经发出去的内容」。
  同时补上三条以前只写在设置页的边界：**不声称供应商零保留**、
  **不探活 / 不查模型列表 / 不查余额**、**代理可见 Key 与摘要且本仓库不提供代理程序**。
- **理由**：这一页是对外的**事实声明**，而「假话」有两种：说了没做到的（过度承诺），
  以及把已做到的继续说成没做到（AI-4 之后的那两句）。两者都会让用户做出错误判断——
  前者让他误以为数据不会出站，后者让他以为功能不可用。改文案时同一条测试断言也要改，
  否则测试就成了「测试自己在测自己」。
- **影响**：隐私页测试的断言从「钉某个字符串」改成「钉**当前真实状态**」并写明每次改动的原因。
  另外把 `LOCAL_ONLY_PARAGRAPHS` 里「不注册 Service Worker、不读写 localStorage / Cookie」
  这条保留（步骤13 加 SW 时它必须一起改，那时它会再次成为检查点）。

## D-082 文档与实现的一致性用**扫描**守住，而不是靠自觉（AI-7）

- **决定**：`acceptance.test.ts` 同时扫描仓库与 `dist/`：
  ① 任何 `sk-` 形状的长串只允许出现在**合成值白名单**里（当前三个，逐条写明用途）；
  ② 禁止出现第三方统计 / CDN 主机名（`googletagmanager` / `google-analytics` / `jsdelivr` /

- **理由**：这三条都是「一旦违反就是发布级事故」的红线，而它们都**不是**类型系统或常规单测能发现的：

## D-083 Service Worker **手写**，用白名单而不是默认运行时缓存（步骤13）

- **决定**：不引入 Workbox / vite-plugin-pwa，自己写 `public/sw.js`（约 200 行，含注释）。
  缓存范围是显式白名单：导航页（网络优先、失败回退缓存壳）、`/assets/*` 等带内容哈希的静态资源
  （缓存优先）、manifest 与图标、SW 自己排除在外。**四条直接放行**：非 GET（AI 调用是 POST）、
  跨源（AI 端点与任何第三方）、带 `Authorization` 的请求、非 http(s)（blob / data 的报告导出）。
  不使用 Background Sync / Periodic Sync / Push / Notification，也从不读写
  IndexedDB / localStorage / Cookie。新版本装好**停在等待**，只有界面收到用户点击后发
  `SKIP_WAITING` 才接管。
- **理由**：本项目对 SW 的要求绝大部分是**否定式**的（不缓存用户数据、不排队、不重发 AI 请求、
  不碰加密仓）。Workbox 的价值在于「常见策略开箱即用」，而它的默认运行时缓存会把
  **未预缓存但同源**的响应也自动存下来——那正好是我们要一条条排除的东西；要关掉得逐项配置，
  反而比手写更难核对（而且要引一个几十 kB 的依赖）。
- **影响**：代价是版本与缓存清理要自己处理，因此这两件事写得很直白并有测试：
  缓存名带版本、`activate` 只删**同前缀**的旧缓存、不调用 `clients.claim()`。
  `pwaAssets.test.ts` 用否定式断言把它们钉住——以后有人想「顺手加个后台同步」或
  「顺手把响应都存起来」，测试会先失败。

## D-084 两套 CSP 由**构建模式**决定，meta 与 `_headers` 同时给（步骤13）

- **决定**：`src/lib/csp.ts` 是策略的唯一来源；`vite.config.ts` 的 `dsh:csp` 插件在构建时把同一份
  字符串注入 `index.html` 的 meta（位置在 `<meta charset>` 之后、任何 `<script>` / `<link>` **之前**）
  与产物里的 `_headers`（Cloudflare Pages / Netlify）。模式由 `vite build --mode ai` 或
  `CSP_MODE=ai` 决定，默认 `local`（`connect-src 'none'`）。自建代理只能通过 `CSP_CONNECT_SRC`
  显式给出**一个精确 https origin**，非法值让构建失败。三种 npm 脚本：
  `build`（本地版）、`build:ai`、`build:subpath`（`--base=`）。
- **理由**：① 策略字符串若在构建配置、部署模板、README 里各写一遍，早晚出现「文档说 'none'、
  产物里是 `*`」这种**看不出问题**的状态——`deploy/vercel.json` 与代码的一致性因此由测试断言；
  ② 不用 shell 语法设环境变量（Windows 下 npm script 里 `VAR=x cmd` 不可用），改用 Vite 自己的
  `--mode` / `--base`，零依赖且跨平台；③ meta 必须排在资源标签之前，否则它只覆盖「之后的」请求，
  这正是 PRD 18.6 说 meta 不等价于响应头的原因之一，产物里因此两个都给。
- **影响**：`src/lib/csp.ts` 刻意**不 import 任何应用层模块**（`tsconfig.node.json` 是 `nodenext`，
  无扩展名的导入链会整串报错），官方 origin 因此写了一份字面量——由测试断言它与
  `AI_DEFAULT_DESTINATION.origin` 相等，两处漂移会立刻失败。
  另外**刻意不加** `upgrade-insecure-requests`：它会把 AI-6 支持的「回环地址本地代理」
  （`http://127.0.0.1:8787`）静默改写成 https 并失败。`style-src` 里的 `'unsafe-inline'` 是唯一
  宽松项（React / ECharts 写内联 style 属性），`script-src` 保持严格。

## D-085 PWA 图标由仓库内脚本生成，不引图片依赖（步骤13）

- **决定**：新增 `scripts/make-icons.mjs`，用 Node 内置 `zlib` 手写 PNG（签名 + IHDR + IDAT + IEND +

- **影响**：`read_image` 已目视确认图形正确（深色圆角方块 + 白 / 紫 / 白三柱）。
  若以后要换成设计稿，替换脚本里的绘制函数即可，测试会保证输出仍是合法的 8 位 RGBA PNG。

## D-086 「更新不丢加密仓」是结构性的，不是承诺（步骤13）

- **决定**：Service Worker 只管理**静态资源缓存**；招聘数据、清洗设置与 AI 历史都在加密仓
  （IndexedDB）里，`sw.js` 从不读写 IndexedDB / localStorage / Cookie（源码扫描断言）。
  版本更新的清理只发生在 `caches` 命名空间内，且只删**同前缀**的旧缓存；
  更新本身由用户点击触发，不在后台自动刷新页面。
- **理由**：这一步最容易被误解的承诺是「更新不丢数据」。把它说成承诺很弱（下一个人加一句
  「顺手清一下缓存」就可能弄坏），做成结构性事实才可靠：两条存储路径根本不相交。
- **影响**：界面文案（`pwaText.ts`）如实写清「刷新只换静态资源，本机加密仓里的数据集、
  清洗设置与 AI 历史都不受影响，也不需要重新导入」，并且**不承诺**「不会丢数据」这种更大的话
  ——浏览器回收存储、清理站点数据仍然会丢（见 `PRIVACY.md` 与站内隐私说明）。
## D-087 jsdom 交互用例与 Playwright 端到端**分工**，而不是二选一（步骤14）

- **决定**：交互层分两档写：**jsdom + Testing Library** 覆盖「组件契约」——映射确认与阻断、
  筛选与引擎读数一致、AI 确认流的一次性令牌与载荷一致性（18 例，走 `npm test`，秒级）；
  **Playwright 驱动系统 Chrome** 覆盖「只有浏览器才能回答的事」——真实请求与 CSP、
  真实 IndexedDB / Cache、Service Worker 生命周期与断网、性能数字（11 例，独立脚本）。
  Playwright 用 `channel: 'chrome'` 驱动本机已装的 Chrome，**不下载浏览器二进制**。
- **理由**：① jsdom 里 `fetch`、CSP、Service Worker、Cache Storage 都不存在或不可信，
  把「零出站」「SW 装上」「断网可用」写成 jsdom 用例等于自欺；② 反过来，把每条组件契约都放到
  Playwright 里跑会让反馈从秒级变成分钟级，且端到端用例更脆。
  ③ 不下载浏览器二进制与「不往仓库塞大文件 / 不引 CDN」的既有约束一致，也让本机零配置可跑。
- **影响**：`tests/e2e/` 与 `src/**/*.test.tsx` 是两套命令（`npm test` 与 `npm run test:e2e`），
  两者都要绿；`tsconfig.e2e.json` 挂进 `tsconfig.json` 的 references，因此端到端用例同样过
  `npm run typecheck`（`noUnusedLocals` 也开着）。测试产生的 `test-results` / `playwright-report`
  进 `.gitignore`，并被仓库守卫的跳过名单排除——**守卫扫的是仓库内容，不是运行残留**。

## D-088 两套构建模式与 `@ai-build` 标签：跑错产物时必须 skip，不许假装通过（步骤14）

- **决定**：AI 相关端到端用例打 `@ai-build` 标签，只由 `npm run test:e2e:ai`
  （`npm run build:ai` + `--grep @ai-build`）运行；`npm run test:e2e` 构建本地版并
  `--grep-invert @ai-build`。用例自己先读页面 meta CSP，若不含官方端点就 `test.skip` 并写明
  「请用 npm run test:e2e:ai」。
- **理由**：本地版 `connect-src 'none'` 下 AI 请求**根本发不出去**，用它验证「确认后恰好一次请求」
  得到的是一个恒真的断言（永远 0 次也能「通过」）。skip 是诚实的第三种状态，
  「通过」不是。
- **影响**：实测在本地版产物上跑 AI 用例为 **2 skipped**；两个 npm 脚本各自先构建对应模式，
  因此不会出现「拿旧产物跑新断言」的情况。spec 文件里也用 `page.route` 拦下官方端点
  （含 CORS 预检），整轮端到端**不产生任何真实外发流量**，也不使用真实 Key。

## D-089 meta 版 CSP 去掉 `frame-ancestors`：只有生效的指令才该留在 meta 里（步骤14）

- **决定**：`src/lib/csp.ts` 新增 `buildMetaCsp(mode, override?)`：与 `buildCsp` **逐字相同、
  只去掉 `frame-ancestors`**。`vite.config.ts` 注入 `index.html` 的 meta 用它；
  `_headers`（响应头形式）仍用完整版。测试钉住三件事：完整版带 `frame-ancestors 'none'`、
  meta 版不带、**把那一行加回 meta 版必须逐字还原成完整版**。
- **理由**：`frame-ancestors` 通过 meta 下发时**按规范不生效**，Chromium 会打印
  `The Content Security Policy directive 'frame-ancestors' is ignored when delivered via a <meta> element.`
  并忽略它（步骤14 的 Playwright 用例在真实 Chrome 里抓到了这条控制台错误）。
  留着它不是「多一层保险」而是**负收益**：常驻一条红色报错会淹掉真正的问题，还会让人以为
  meta 也防住了点击劫持。点击劫持防护的真实归属是 `_headers` 里的响应头 CSP 与
  `X-Frame-Options: DENY`（任何平台都生效）。
- **影响**：PRD 18.6 与 `deploy/github-pages.md` 里「meta CSP 不等价于响应头策略」这句话
  第一次在代码与产物里落地，而不是只写在文档里。`pwaAssets.test.ts` 与 `lib/csp.test.ts`
  各自断言产物 / 函数层面的这条差异，两边漂移会失败。

## D-090 性能只记**实测数字**并只对「明显退化」设上界（步骤14）

- **决定**：`tests/e2e/performance.spec.ts` 记录并把数字落盘到 `test-results/perf-baseline.json`：
  首屏 `load` 耗时、首屏脚本文件字节数（口径 = 直接读 `dist/index.html` 引用的
  `script` / `modulepreload` 文件大小求和）、首屏资源请求数与同源性、整条本地链路墙钟耗时、
  最长长任务。断言只设「明显退化」的上界（8 s / 1.6 MB / 30 s / 5 s），并断言首屏入口脚本
  **不是** `echartsRegister` / `xlsx` / `parse.worker` / `vault-`。
- **理由**：① 本项目没有承诺任何性能指标，把某个数字写成「必须更快」是编造需求；
  真正要防的是**结构性退化**（图表或解析库被静态 import 进首屏），那条用「入口脚本不是谁」来断言
  比用体积阈值更准；② 浏览器报的 `encodedBodySize` 受缓存与服务器压缩影响
  （实测本机 `vite preview` 对真实 GET 会 gzip，于是主 chunk 报 229,862 B，而文件是 760,093 B），
  换台机器不可比，因此它只作旁证，断言口径用**文件大小**；③ 数字必须落盘，
  否则「性能基准」会退化成一句「跑过了」。
- **影响**：`docs/ACCEPTANCE.md` §0 抄录了实测值（首屏 `load` 133 ms、首屏脚本 832,572 B、
  请求 7 个全部同源、链路 1232 ms、最长长任务 60 ms），并在 `KNOWN_ISSUES.md` §2.6 写明
  这些数字**不含**低端设备与几万行真实数据量。

## D-091 手动修正属于**清洗输入**，不是界面状态；且必须换配置摘要（用户需求 ①，**已实现**）

> 本条的口径在发布前人工验收期间定下（用户当时选择「先验收、后开发」），**现已按此实现**：
> 异常项清单（`features/cleaning/IssueWorklistPanel.tsx`）提供「修改这一格」，修正写回
> `CleaningSettings.manualCorrections`（清洗输入），参与配置摘要；实现细节与测试见本条末尾。

- **背景**：清洗预览页已有「质量标记」列（逐行问题徽章）与展开后的「原值 → 清洗值 → 命中规则」，
  但**没有**「只看异常行」的筛选，也**没有**任何改值入口。用户在真实名单（83 行）上发现
  「逐页找徽章」不可用，提出要「标注异常 + 手动修正」。
- **决定**（四条硬约束，缺一条都会破坏已有不变量）：
  1. **修正是清洗的输入**：新增 `ManualCorrection = { sourceSheet, sourceRow, field, correctedValue, reason, correctedAt }`，
     由 `src/cleaning` 在清洗时应用并产出新的 `NormalizedDataset`。`NormalizedRecord` 是冻结的只读结构，
     **组件不得就地改它**，也不得把修正存成组件 `useState`（离开页面即丢，且会让看板/报告/导出各算一份）。
     这与「清洗口径只在 `src/cleaning`」是同一条纪律。
     **实现时的修正（与计划不同，必须说明）**：定位键不用 `recordId`，用
     `sourceSheet + sourceRow + field`——清洗每次都会重算 `recordId`，用它当键会让「改完一提交、修正就找不到目标」
     （用户看到的现象是「改了没生效」）。行号是原始表里的位置，重清洗也稳定。
  2. **修正会改变统计结果 → 必须换配置摘要**：修正必须进 `CONFIG_REVISION_FIELDS`（唯一清单）并补测试，
     同时随 `metadata.cleaningSettings` 写进数据集快照。否则「同一份数据两次分析结果不同」无法解释，
     也就是 AGENTS §9 要防的那件事。
  3. **回溯链不能断**：展开视图必须同时在场 —— 原值 / 自动清洗值 / 手动修正值 / 修正原因 / 修正时间；
     `normalizationLog` 追加一条 `rule: 'manual-correction'`、`source: '用户手动修正'`、`confirmed: true`。
     修正后该行的问题码要**按重新清洗的结果重算**（该消失就消失），质量报告计数与变更影响预览同步更新。
     修正值属于业务数据，**不进** AI 摘要、不进日志，也不写进质量报告的 `rawValue`（那里只允许单格原值）；
     导出仍走唯一 `SanitizedReport` 闸门，并在报告里注明「含 N 处手动修正」。
  4. **缺失 ≠ 0**：把值修正为空白必须是 `null`；「恢复原值 / 撤销修正」是一等动作，不是隐藏操作。
- **粒度决定（用户勾选了全部六类问题）**：不做「一个通用输入框」，按三种粒度设计 ——
  **字段级**（日期类、缺失必填项：逐行逐格）、**枚举 / 单位级批量**（未识别枚举、薪资与房补单位、
  区间值、实物住宿、GPT 名单冲突：按「原值 → 取值」成组确认，能落到设置层的优先走设置层）、
  **组级**（重复行判定：复用现有 `DuplicateReviewPanel` 的逐组确认，不另造第三套确认范式）。
- **一个设计判断**：`PLANNED_DATE_UNCERTAIN`（计划日期语义待确认）来自「待入职行拿『入职时间』
  当计划日期」这一**列语义不确定**，不是某格写错。逐行改值等于把 1 个口径问题变成 N 条例外；
  优先在设置层显式选择「计划周期日期来源」，行级修正只作兜底。
- **影响**：本步会改清洗层、配置摘要、报告与导出边界，因此**步骤14 的验收结论在开工后作废**，
  必须按新版本重跑 `typecheck` / `lint` / `test` / 三种构建 / 两种端到端并重判
  `docs/ACCEPTANCE.md` 的 A02 / A05 / A06 / A12 / A15。范围与影响面见 `docs/IMPLEMENTATION_PLAN.md` 的「步骤15」。
- **实现（本条已落地，2026-09-27）**：
  - `src/cleaning/normalize.ts`：`applyManualCorrections` 走**两遍**——先按原值算出基线清洗结果，
    再把被修正的格子替换成新值重算该行，因此新值本身仍要过同一套校验，不是绕过清洗；
    `normalizedValueOf` / `correctionsApplyTo` 是唯一判定点；
  - `src/cleaning/sheetSignature.ts`：`sheetSignatureOf(sheet)` 给「表结构 + 内容」算一份摘要（不含文件名）；
    修正只在摘要一致时应用，换表后旧修正不套用到新表（否则会出现「改的是 A 表的第 5 行，却改了 B 表」）。
    摘要存进 `CleaningSettings.manualCorrectionsSheetSignature`；
  - 清洗日志的对应条带 `autoValue` / `reason`，界面五栏（原值 / 自动清洗值 / 手动修正值 /
    修正原因 / 修正时间）直接读它，**不另存一份**；
  - 新问题码 `MANUAL_CORRECTION_APPLIED`（已应用，警告，不禁用模块）；
  - 界面：`features/cleaning/IssueWorklistPanel.tsx` 提供「只看异常行」清单 + 严重度 / 问题码筛选 +
    「修改这一格」弹窗（原值、自动清洗值、新值、**原因必填**）+ 撤销；文案在 `manualFixText.ts`；
  - 测试：`src/cleaning/manualCorrection.test.ts` **7 例**、`IssueWorklist.interaction.test.tsx` **2 例**，
    覆盖「原因必填才可提交」「改空白 = null 而不是 0」「撤销后逐字节回到原样」「换表后修正不生效」。

- **背景**：PRD 5.2 早就承诺「渠道『-』且推荐人为内推 → 可选择推断渠道为内推；默认仍为未知」，

## D-093 薪资直方图：取值少时**按每个实际取值一柱**，取值多时才等宽分档（图表反馈 ①）

- **背景（用户的原话）**：真实名单里的薪资只有 3500 / 4000 / 4500 / 5000 / 5500 这几个值，
  屏幕上的直方图却按等宽 8 档画，大多数柱子是空的，看起来像「数据有问题」。
- **决定（用户在三选一中选了 A）**：分档规则按**取值个数**分流 ——
  - 不同取值 ≤ 12（`VALUE_BIN_MAX_DISTINCT`）→ **每个实际取值一柱**（区间退化为单点，`to: null`，柱标签就是取值本身）；
  - 不同取值 > 12 → 保持原来的**等宽 8 档**；
  - 两种情况的图下都出一句 `histogramNote`，**写明当前用的是哪一种**，不让用户自己猜。
- **为什么不直接把等宽档数调小**：档数调小会让长尾数据（几百到几千）全部挤进一两柱，
  反过来丢掉分布形状；而「取值少」和「取值多」本来就是两种数据，用同一个档数伺候必然有一头是错的。
- **为什么阈值是 12**：12 个取值在 8 档等宽下必然出现空格子，正好是要修的现象；
  12 也是横轴分类能读得出来的上限（与 `CHART_CATEGORY_MAX_LENGTH` 的用意一致）。
- **实现**：`domain/analytics/compensation.ts` 的 `buildHistogram`（唯一分箱点）+ `histogramNoteOf`。
- **影响**：分箱是**展示层口径**，不改任何计数与分位；P25 / P50 / P75 与均值一概不变。
  原先断言「一律等宽 8 档」的 2 个用例改为**两条分支都覆盖**。

## D-094 图表排序 / 横竖方向 / 截断属于**展示规则**，导出图不保证同步（图表反馈 ②③）

- **背景**：用户提出三条：①柱子应当**从高到低、从左到右**排；②横轴文字显示不全（怀疑是字号问题）。
  实际原因是分组名长（如岗位全名）在竖排时被容器挤掉，不是字号。
- **决定**：
  1. **排序**：分组柱状图默认按该图声明的指标**降序**（`sortGroupsForChart`，`sortBy: 'value-desc'`）；
     率线（`rateLines`）**必须跟着柱子一起重排**，否则会出现「率线配错柱子」——那比不排序严重得多；
     保留 `sortBy: 'input'` 以应付「必须按业务顺序看」的图。
  2. **横竖方向**：分组名长的图（时间效率、学校）改用**横向条形**（`layout: 'horizontal'`），
     名字直接完整显示；横向布局不画率线（一格两套刻度的横向图读不出来），率仍在下方的数据表里。
  3. **截断**：竖排确实放不下时截断为「前 8 个字符 + …」（`truncateCategoryLabel`），
     完整名字保留在数据表与提示里，**不靠缩小字号**（用户猜的方向；缩小字号只会让小屏上更难读）。
  4. 下钻点击改用 ECharts 的 `dataIndex` 回查原始分组键再传出去：
     排序后「第 3 根柱子」不再等于「第 3 个分组」——**这是排序引入的真 bug，已修**。
- **导出边界（如实记录）**：Excel / Markdown **只有数据表没有图**（原有设计不破）；
  PNG / 打印 PDF 里的图走**另一条**离屏重绘路径（`exporters/png.ts` 的 `buildChartSpecsFromReport`）：
  它按**脱敏报告里的分组顺序**（不是界面上的降序）出图，每个维度只画 N 与 D 两条序列，且始终竖排。
  这样做是刻意的——导出图只能消费 `SanitizedReport`（分组标签已脱敏：HR 是代号、小区组已并、被抑制组不画），
  界面上的排序与横竖方向属于**展示偏好**，不能反过来决定报告里有什么。
  因此「导出的 PNG 与屏幕上的图不完全一样」是**已知限制**，已记进 `docs/KNOWN_ISSUES.md`（P2），
  **不写成「已实现」**；修它的成本与收益见该条。

## D-095 薪资计薪口径默认「人民币元/月」：给默认值，但仍然不换算、不逐行猜（用户反馈 ①）

- **背景**：PRD 5.3 与 `SALARY_UNIT_OPTION_DEFS` 早就把「人民币元/月」标成「**建议**默认值，仍需用户在导入页确认」，
  但 `createDefaultCleaningSettings` 实际给的是「暂不确定」。用户的实际名单就是元/月，
  于是每次导入都要手动选一次，否则待遇对比与低薪标签默认被禁用（他看到的是一块被禁用的模块）。
  用户 2026-09-27 明确要求：**薪资计薪口径默认为 人民币元/月**。
- **顺带关闭的开放项**：PRD 附录 B 第 2 条「薪资币种与计薪周期的默认值是否统一为『人民币元 / 月』」
  自此**已确认**（本条就是那条的答复）。
- **决定**：
  1. `createDefaultCleaningSettings` 的 `salary` 改为 `buildSalarySetting('人民币元/月')`
     （`currency: 'CNY'`、`salaryUnit: '元/月'`、`comparable: true`、`confirmedAt: null`）；
  2. **仍然不做任何换算**、也不逐行猜单位：它只是给「币种」与「计薪周期」这两列一个取值，
     金额数值本身原样保留（PRD 5.3「混合月薪 / 日薪不得直接聚合」照旧成立）；
  3. 「暂不确定」保留为可选项：选它仍然禁用待遇对比与低薪标签，问题码 `SALARY_UNIT_UNCONFIRMED` 照旧存在；
  4. **`confirmedAt` 保持 `null`**：默认值不是用户确认的结果，界面据此说「当前用的是默认值，还没有手动改过」，

- **为什么不选「默认元/月但仍要求再点一次确认」**：那等于把用户明确的请求又变成一次点击，
  收益只是形式上的洁癖；真正要防的是**标错口径**，而这条由「界面上写清当前用的是默认值 + 一键可改」防住。

  旧数据集与旧报告保存的是它们当时那份摘要，**旧报告不变**，重新提交的数据集才按新默认。
- **残余风险（已记录）**：如果名单里混有按天计薪或外币的行而用户没有改口径，
  这些行会被标成「CNY / 元/月」。这是**用户必须自己核对**的一项，已写进 `docs/KNOWN_ISSUES.md` §2.10；
  我们不用「金额小于某个数就猜是按天」这类阈值替用户判断（那会把一个口径问题变成一堆猜测）。
- **测试**：`src/cleaning/settings.test.ts` 改写为断言新默认（含 `confirmedAt === null`）与
  「暂不确定仍可显式选择」；`src/cleaning/normalize.test.ts` 的「未确认」分支改为**显式**传该设置，
  并新增 1 例断言默认口径下币种 / 周期被标注、不再产生未确认问题。

## D-096 打印版窗口是空白页：`window.open(..., 'noopener')` 返回 null（用户反馈 ③，真 bug）

- **用户看到的现象**（截图）：点「打印 / 另存为 PDF」之后开出一个**空白标签页**，
  没有下载、也没有打印对话框；界面上给出的提示是「导出未完成：浏览器拦截了新窗口」。
- **根因**：代码写的是 `window.open('', '_blank', 'noopener,noreferrer')`。
  带 `noopener` 时浏览器**返回 `null`**（这是规范行为，不是浏览器 bug），于是：
  ① 我们拿不到窗口引用、一个字都写不进去；② 走进 `=== null` 分支，判定成「被弹窗拦截」。
  用户看到的是「明明开了一个空白页，却说被拦截了」——**提示语与事实不符**，比空白本身更误导。
- **为什么一直没被发现**：jsdom 不会真的开窗口，单测看不见；
  v1.2.1 的端到端用例只点到「生成并查看预览、四个按钮可用」为止，**没有点过打印那一颗**。
  与导出闸门那两个 bug 属于同一类：**自动化没覆盖到的那一半**。
- **修法**：用**普通** `window.open('', '_blank')` 拿引用，然后在写内容之前手动 `opened.opener = null`
  （防护效果与 `noopener` 相同：新窗口拿不到 `window.opener`、不能反向操纵本页；但我们保住了引用）。
  `AiResultPanel` 的 AI 结果打印版**同一个写法、同一个 bug**，一并修掉。
- **守卫（这一条不能只靠「这次记得」）**：
  - 真实浏览器用例（`tests/e2e/local-flow.spec.ts`）真的点打印，断言新窗口里
    调用过 `print()`、正文含「数据截至日」、正文长度 > 200（空白页会是 0）——
    修复前这条用例**先跑失败**，失败信息里正好是那句「浏览器拦截了新窗口」，这就是根因的证据；
  - 仓库扫描 `src/features/export/printWindow.test.ts` 禁止任何 `window.open(` 的同一条语句里出现
    `noopener`（扫之前先剥掉注释，因此注释里可以继续写明这个坑）。
    我另外用一个临时探针文件验证过这条扫描**真的会失败**，不是一条永远绿的摆设。

## D-097 「返回全部数据」放在每个模块的标题栏：用作用域，而不是 12 处传 props（用户反馈 ②）

- **背景**：用户需求 ④ 当初只在三处下钻旁放了「返回全部数据」（状态结构 / 时间趋势 / 分维度分析面板）。
  用户实际用下来发现：分维度分析有 8 个模块，下钻之后视线停在**某一个模块**的表格上，

## D-098 AI 错误分类顺序：401 / 402 / 429 先于 `error.code`（用户实测误诊后修正）

- **真实经过**：用户配好自己的 Key 后第一次真发请求，界面报
  「请求参数被服务端拒绝（可能是模型不支持某个参数，或摘要长度超出模型上下文）」
  并给出「请检查模型与参数…」的建议；而同一段文字里的**服务端说明**写着
  `Authentication Fails, Your api key: ****ca87 is invalid`（HTTP 401、`error.code = invalid_request_error`、
  `error.type = authentication_error`）。**真正的原因是 Key 无效，界面却把他引向参数与模型。**
- **根因**：`errorKindOfCode` 的判定顺序是「`error.code` 优先、HTTP 状态兜底」，
  而 DeepSeek 在「Key 无效」时给的 `code` 恰好是**通用的** `invalid_request_error`。
  于是 `invalid_request_error` 先命中 → 判成 `invalid-params` → 提示与建议整套都错。
  也就是说：**「官方 code 更精确」这个前提在 401 这一档上不成立**（DeepSeek 把认证失败也标成了它）。
- **新顺序（写死不靠记忆）**：
  1. `401` → `auth`、`402` → `balance`、`429` → `rate-limit`（这三个状态与语义一一对应，没有歧义，**先判**）；
  2. 再看 `error.type`（官方字段，粒度更粗但更贴近语义——本例里它是正确的那个）；
  3. 再看 `error.code`；
  4. 其余状态兜底（`400` / `422` → 参数、`404` → 模型、`5xx` → 服务端）。
  这**不是**「状态一律优先」：`422 + insufficient_balance` 这类仍按 `type` / `code` 判成余额不足，
  只有上述三个状态被提前。
- **顺带修的提示语**：`auth` 的建议从「请替换 Key 后重新预览并确认」改成
  「请检查这把 Key：是不是复制少了字符 / 多带了空格换行、是不是在 DeepSeek 平台上被删除或重置、
  账户是否可用；换一把有效 Key 后重新预览并确认。本应用不会打印或回显 Key，也不会自动重试。」
  ——把用户真正能自己排查的三件事写出来（原句太笼统，等于没说）。
- **服务端说明照旧原样带回来**：这一条不能删——用户这次正是靠它看懂原因的。
  它被截断（`AI_ERROR_DETAIL_MAX_CHARS`）、且不含 Key 与请求正文。
- **测试**：
  - `src/ai/aiResult.test.ts`（新增 4 例）钉住判定顺序，含本次的真实组合
    `401 + code=invalid_request_error + type=authentication_error` → `auth`，
    以及「`422 + insufficient_balance` 仍按语义判」这类**反向**用例（防止把状态优先写过头）；
  - `src/ai/aiClient.test.ts` 新增 1 例：用服务端真实返回的**形状**（Key 掩码用合成值 `****0000`）
    断言 `kind === 'auth'`、提示含「认证失败」、**且不再出现「参数被服务端拒绝」**、建议里不含「检查模型与参数」。
- **教训（与 §1.0.4 / §1.0.5 同类）**：这一条也是**只有真实调用才会暴露**的问题——
  我们此前所有 AI 用例用的都是合成响应，从没喂过「真服务端的错误形状」。已经把它变成用例。

## D-099 「HTTP 成功但正文为空」必须分情况诊断，并在参数区提前说明思考模式占用额度

- **真实经过（同一次会话的第二次调用）**：用户换好 Key 后再发一次，这次 HTTP 是成功的，
  但界面报「响应里的 content 为空或缺失…稍后重新预览并确认；若持续为空，请检查模型与参数」。
  那句话**等于没告诉他该改哪里**——而他当时用的模型 `deepseek-flash` 的
  **思考模式默认为开启**（我们自己的模型目录里就写着 `thinkingDefaultEnabled: true`），
  推理内容**与正文共用 `max_tokens`** 这一个额度，2048 被推理吃光后正文自然是空的。
- **决定（两条，缺一条都还会让人卡住）**：
  1. **报错要分情况**（`client.ts` 的 `emptyContentError`）：
     - `finish_reason === 'length'` → 「模型把输出额度用完了，正文没有产出」，
       建议「把思考模式设为关闭、或把最长输出调大（例如 8192）」；
     - 响应里存在 `reasoning_content` 或 `reasoning_tokens > 0` → 「服务端这次只产出了推理内容，
       正文为空；本应用按要求不读取推理内容」→ 建议关闭思考模式或改用不支持思考的模型；
     - 两者都读不到 → 保留原来那句泛泛提示（但建议里补上「先确认模型的思考模式」）。
     三种情况都把**事实**带出来：`finish_reason`、本次产出 token 数、其中推理 token 数。
  2. **界面提前说**：当「思考模式 = 不指定」且所选模型 `thinkingDefaultEnabled === true` 时，
     参数区直接写明「这个模型的思考模式默认为开启，推理内容与正文共用最长输出上限」。
     这正是用户当时最需要、而我们没给的一条信息——它本来就在我们自己的模型目录里。
- **关于「不读 reasoning_content」的边界（这一条不能松）**：
  新代码只检查该字段**在不在**、以及推理 token 的**计数**，**不读、不存、不显示它的正文**。
  计数与字段存在性是定位问题所需的元数据；正文一旦读了就有被展示或外发的风险。
  测试里专门断言推理正文**不会**出现在错误对象里。
- **测试**：`aiClient.test.ts` +2 例（`finish_reason=length` + 推理 token 计数 → 提示含「额度用完了」
  与 `finish_reason=length`；只产出推理 → 提示含「不读取推理内容」且**错误对象里搜不到推理正文**）、
  `AiAnalysisWorkspace.test.tsx` +1 例（默认模型显示这条提示；换成思考模式默认关闭的模型、或用户
  自己把思考模式设为关闭时都不显示）。
- **影响**：只是**提示与诊断**的变化，没有改请求参数、没有改脱敏、也没有碰任何出站边界。

## D-100 AI 偏好要有「本会话兜底」，并允许在看板原地配置（用户反馈，真 bug + 体验）

- **真实经过**：用户在**设置页**打开了 AI 开关（当时没建本地仓，界面如实提示
  「配置已在本次会话生效，但没能写入本地仓」），切到**分析看板**后看板仍写着
  「AI 深度分析当前是关闭状态（默认关闭）」，**预览按钮点不动**。
- **根因（提示语与实现不一致）**：`loadAiSettings()` 每次都只去仓里读，读不到就回落默认值；
  临时模式下用户的选择**从来没进过仓**——所谓「本次会话生效」实际只对设置页那一个页面成立。
  换句话说：**提示语承诺了「会话」，代码只做到「页面」。**
- **决定 1：偏好加一层本会话兜底**（`src/ai/aiSettings.ts` 的 `sessionOverride`）：
  写仓失败时记住用户的选择，`loadAiSettings` 优先返回它；**一旦写仓成功就清掉**，
  仓重新成为唯一事实来源（因此解锁一个已存偏好的仓时，仓里的值会正常生效，不会被内存空值盖住）；
  `removeAiSettings`（清空 AI 配置）会一并清掉它，避免「清空后界面还拿内存副本当配置」。
  它只是**模块级内存**，刷新即失——与「临时模式只在内存」的既有口径一致，**没有新增任何落盘**。
- **决定 2：允许在看板原地配置 AI**（用户原话：「把设置里 AI 相关的信息放到分析看板中来，
  交互应该是 分析看板 → AI 深度分析 → 填写 API → 确认分析」）：
  `AiAnalysisWorkspace` 增加一个**槽位** `settingsSlot`，看板把**设置页正在用的同一个**
  `AiSettingsPanel` 塞进去（同一个组件、同一份口径、同一条保存路径），
  默认在 AI 未启用时展开（那正是用户需要看到开关与 Key 输入框的时刻）。
  为什么用槽位而不是让 `features/ai` 直接 import 设置面板：那会把两个功能区的边界搅在一起，
  而槽位只要求「一块内容」。**设置页那块面板照旧保留**，两处不冲突。
- **决定 3：面板与宿主状态必须同步**：`AiSettingsPanel` 新增 `onSettingsChange`，
  每次保存（无论是否写进仓）都把最新偏好回传。看板据此更新自己的 `aiSettings`，
  否则会出现用户实际看到的那种矛盾画面：**面板里开关是开的，旁边却写着「已关闭」**。
- **测试**：`aiSettings.test.ts` +2 例（写仓失败时本会话读回来仍是刚选的那一份；
  「清空 AI 配置」会一并清掉会话态）、`AiAnalysisWorkspace.test.tsx` +1 例
  （槽位渲染与默认展开、不传槽位时一个字都不多）。

## D-101 只是打开清洗预览页不该作废已提交的数据集（用户反馈，真 bug）

- **真实经过**：用户说「有时候已经上传了数据，但重新进入分析看板，又要重新确认清洗预览」。
- **根因**：`CleaningEditor` 里那个「编辑即写回会话草稿」的 `useEffect` **在挂载时也会跑**，
  而 `saveCleaningSettingsDraft` 的语义是**「设置变了 → 已提交的结论作废」**
  （数据集必须与产生它的那份设置一一对应）。两者叠在一起的结果是：
  **只要打开（或只是回到）清洗预览页、一个字都没改，刚提交的数据集就被扔掉了。**
- **决定**：effect 加两道门——① **首帧只记基线、不写回**（挂载不是一次编辑）；
  ② 之后只有与基线**确实不同**才写回，比较用清洗层的规范键 `cleaningSettingsKey`（不自己拼字段）。
  于是数据集的作废条件回到它本来的语义：**改了设置才作废**。
- **为什么不去改 `sessionStore`**：那条「设置变 → 结论作废」的不变量是对的，
  错的是**在挂载时触发了它**。把不变量挪走会让「旧结论配上新设置」这种更难查的问题回来。
- **测试**：新增 `CommittedDataset.interaction.test.tsx`（jsdom 真实渲染 2 例）：
  ① 挂载后数据集仍在（修前会失败）；② 真的改一个设置后数据集确实被作废（口径没被修丢）。
- **仍未解决的同类问题（如实记录）**：数据集本身**只在内存**，
  所以**刷新页面 / 闲置 15 分钟自动锁定 / 手动锁仓 / 关掉标签页**之后仍需重新导入。
  把提交的数据集加密写进本地仓并在解锁后恢复，是 `docs/KNOWN_ISSUES.md` §2.3 记着的那一步，
  **本轮没有做**（它会往本地仓里写用户的名单，属于需要用户明确同意的一步）。

## D-102 「这一份产物能不能用 AI」由页面自己的 meta CSP 决定（公开发布前的诚实性修正）

- **背景**：用户要把工具放到腾讯云给同事用（需求 A、不含 AI）。这时发现一个**界面与事实不符**的地方：
  本地版（`connect-src 'none'`）与含 AI 版的界面**一模一样**——本地版里照样能看到「AI 深度分析」按钮、
  能打开开关、能生成预览，直到点下确认才被自己的 CSP 拦下，并收到一句
  「可能是网络中断、DNS / TLS 问题，也可能是跨域预检被拒绝」——
  **这三种都不是**：是我们按「不含 AI」构建的。让每一位公开访客走进这条死路，违反
  「提示语必须与事实一致」。
- **决定**：新增 `src/lib/aiAvailability.ts`，**读页面自己的 meta CSP**（构建时由 `src/lib/csp.ts`
  注入的唯一来源）判断这一份产物有没有出站能力；判据只有一条：`connect-src` 恰好是 `'none'`。
  命中时：看板不发 AI 入口、设置页不摆 AI 面板，改为一句说明
  （`AI_UNAVAILABLE_NOTE`：为什么不可用 + 本地功能照常 + 要用 AI 请用含 AI 的那一份构建）。
- **为什么不用 `import.meta.env.MODE`**：测试环境里它是 `test`，与真实产物不一致；
  而 meta CSP 是**产物里真实存在的那一份**，读它等于读事实。选择器提成
  `CSP_META_SELECTOR` 常量，构建侧与运行时侧共用，避免「属性顺序一改就悄悄失效」。
- **边界（不做超出事实的判断）**：只认 `connect-src 'none'`。含 AI 版、自建代理、
  甚至指令缺失都返回「可用」——「连不连得上」还取决于网络与对方 CORS，那是请求层的事，
  由它如实报错。
- **测试**：`src/lib/aiAvailability.test.ts` 5 例（本地版 → 不可用；含 AI 版 → 可用；
  无 meta → 可用；只有 `object-src 'none'` 不算；那句说明必须同时讲清「为什么」与「本地功能照常」）；
  端到端在**真实浏览器**里断言本地版没有 AI 入口、且显示说明文字
  （含 AI 版的同一处由 `ai-one-shot.spec.ts` 断言按钮存在——两条用例一起证明
  「界面说的是这一份产物真实的能力」）。
- **顺带交付（同一轮）**：`启动本地版.bat` + `scripts/serve-dist.mjs`（零依赖本地服务器，
  双击即用，只监听 127.0.0.1），以及 `deploy/tencent-edgeone.md`（腾讯云上线指南）。
