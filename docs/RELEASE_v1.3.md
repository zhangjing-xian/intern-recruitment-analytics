## 0.1 v1.3.2 改了什么（你拿真实 Key 试了一次之后）

你配好 Key、发了第一次真实请求，服务端回的是
`Authentication Fails, Your api key: ****ca87 is invalid`（HTTP 401），
而我们的界面把这次失败说成「**请求参数被服务端拒绝（可能是模型不支持某个参数…）**」，
还建议你「检查模型与参数」。**这条提示是错的**，会把你引向错误的方向。

| | 内容 |
|---|---|
| 真正的原因 | **认证失败：这把 Key 无效**（不是参数、不是模型、不是摘要太长） |
| 我们的 bug | 服务端在 Key 无效时给的 `error.code` 是通用的 `invalid_request_error`，而我们的判定顺序是「先看 code」→ 于是把它归成了"参数问题" |
| 修法 | 判定顺序改成 **先看 401 / 402 / 429 三个状态 → 再看服务端的 `type` → 再看 `code` → 其余状态兜底**；同时把「认证失败」的建议换成你真正能自查的三件事（复制是否完整、Key 是否被删除/重置、账户是否可用） |
| 证据 | `aiResult.test.ts` +4 例（含这次的真实组合，以及「422 + 余额不足仍判余额」的反向用例）、`aiClient.test.ts` +1 例（用真实返回形状断言不再出现「参数」） |
| 顺带确认的事 | 那次响应带 `request_id`，说明**请求真的到达了 DeepSeek**——浏览器直连没有被跨域（CORS）拦下。这条以前是「未验证」，现在至少**这一半有了真实证据**；成功路径仍未跑通 |

口径与理由见 `docs/DECISIONS.md` **D-098**，现象记录见 `docs/KNOWN_ISSUES.md` §1.0.6。

### 0.1 续：你第二次调用（HTTP 成功但正文为空）

你换好 Key 后再发一次，这次 **HTTP 是成功的**，但界面只说「响应里的 content 为空…请检查模型与参数」。
真正的原因是：**你选的模型 `deepseek-flash` 的思考模式默认为开启**，而推理内容与正文**共用**
「最长输出 max_tokens」这一个额度——当时是 2048，被推理吃光后正文就是空的。

| | 内容 |
|---|---|
| 真正的原因 | 思考模式默认开启 → 推理把 2048 的输出额度用完 → 正文为空（**不是** Key 的问题，也不是网络问题） |
| 怎么改 | 两条都行：把 **思考模式设为「关闭」**，或把 **「最长输出 max_tokens」调大**（例如 8192）；改完**重新生成预览**再确认（改参数会让旧确认失效，这是设计如此） |
| 我们改了什么 | ① 报错分情况：额度用尽 / 只产出推理 / 其它三种，分别给出对应建议，并把 `finish_reason` 与 token 计数写在提示里；② **参数区提前说明**：思考模式 = 不指定且该模型默认开启时，直接写明「推理与正文共用上限」——这条信息本来就在我们自己的模型目录里，之前没告诉你 |
| 边界没松 | 我们仍然**不读**模型返回的推理正文，只检查这个字段在不在、以及推理 token 的**计数**（测试里专门断言推理正文不会出现在错误信息里） |
| 口径 | `docs/DECISIONS.md` **D-099**，现象见 `docs/KNOWN_ISSUES.md` §1.0.7 |

## 2. 一个必须说清的限制：导出的图与屏幕上的图排列不同

- Excel / Markdown：**只有数据表，没有图**（原有设计，没变）。
- PNG / 打印 PDF：图是**本机从脱敏报告重绘**的，走的是另一条路径；它按报告里的分组顺序画、
  每个维度只有 N 与 D 两条计数序列、并且**始终竖排**。因此**导出的 PNG 与屏幕上的图不是同一张**。
- 为什么不一并改：导出图只能消费脱敏报告（分组标签已经是 HR 代号、小区组已合并、被抑制的组不画），
  把「按哪个指标排序、横着还是竖着」从界面传进导出层，等于给导出层开一个能影响出图内容的入口；
  排序只是看图的偏好，不值得为它扩大这个接口。**数字两边完全一致，只有排列与方向不同。**
- 详见 `docs/KNOWN_ISSUES.md` §2.9（记录为 P2，未排期）。

本版实测校验（**准确字节数与 SHA-256 一律以归档外的 `_release/SHA256SUMS-v1.3.4.txt` 为准**：
本文件在归档内部，写死数字就会自相矛盾）：

| 项 | 值 |
