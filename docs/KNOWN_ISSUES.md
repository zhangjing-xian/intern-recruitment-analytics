## 1.0.1 步骤14 已解决：meta CSP 里的 `frame-ancestors` 会被浏览器忽略并报错

- **现象**：真实 Chrome 里每次加载都会打印
  `The Content Security Policy directive 'frame-ancestors' is ignored when delivered via a <meta> element.`
  这条控制台错误是 Playwright 用例「全程零 console error」断言抓到的。
- **为什么必须改而不是「加个豁免」**：`frame-ancestors` 按规范在 meta 里就不生效，留着它只有坏处
  ——常驻一条红色报错会淹掉真正的问题，而且给人「meta 也防住了点击劫持」的错觉。
- **现在的做法**：`src/lib/csp.ts` 新增 `buildMetaCsp`：与响应头版**逐字相同、只去掉
  `frame-ancestors`**；`vite.config.ts` 的 meta 注入改用它，`_headers` 仍用完整版。
  测试钉住三件事：完整版带 `frame-ancestors 'none'`、meta 版不带、
  把那一行加回 meta 版必须**逐字还原**成完整版（防止两边各自漂移）。
- **点击劫持防护的实际归属**：`_headers`（响应头形式，Cloudflare Pages / Netlify 等会施加）
  与 `X-Frame-Options: DENY`（在 `SECURITY_HEADERS` 里，任何平台都生效）。
  这也正是 PRD 18.6 与 `deploy/github-pages.md` 已经写明的那句话：meta CSP 不等价于响应头策略。

## 1.0.4 用户需求验收期已解决：报告导出闸门的两个 bug（v1.2.1 修正）

- **发现方式（值得记住）**：用户在 v1.2.0 上人工验收报告导出页时看到
  「上面写着检查通过、下面写着检查未通过：导出按钮保持禁用」——**两个 bug 都落在自动化从没覆盖到的那一半**：
  步骤11 的验证是 `react-dom/server` 渲染冒烟（只断言文案与禁用态字符串），步骤14 的端到端也没点过这个闸门。
- **bug 1：闸门死锁**。`canExport` 要求 `confirmedFingerprint === fingerprint`，
  而唯一把它写成非空的地方在四个导出按钮自己的 `onClick` 里，那四个按钮偏偏 `disabled={!canExport}` →
  「不点按钮就无法确认，不确认就点不了按钮」→ **导出永远不可用**。
  修正：「生成并查看预览」在生成预览的同时把它记为已查看；改级别 / 明细开关 / 筛选会让指纹变化、
  按钮自动回到禁用态（**闸门没有被削弱**）。
- **bug 2：哨兵误拦**。导出前的「本机已知敏感取值」检查把源列里每一个非空值都当哨兵，
  于是**受控字典词汇永远自撞**：源里写推荐类型「内推」、报告里的渠道标签也是「内推」；
  源里写原因「薪酬」、报告里的原因类别也是「薪酬」→ 判定命中并**阻断导出**。
  实测在演示数据（50 行合成样本）上命中 6 处、四个按钮全部锁死，而那几个字是**类别标签**，不是身份信息。
  修正（`src/features/export/exportSentinels.ts`）：受控字典词汇不进哨兵集合，
  **具体人名**（如「示例推」）与**字典外的自由文本**照旧进。
- **顺带修掉的文案矛盾**：预览过期时导出区写的是「检查未通过」，而检查其实通过了。
  现在四种原因分开说：还没生成预览 / 预览已作废 / 检查未通过 / 这一份预览还没确认。
- **回归证据**：`src/features/export/ExportGate.interaction.test.tsx`(3) 在 jsdom 里走完整状态机
  （预览前禁用 → 生成后可用 → 改级别后作废 → 重新生成再可用）；
  `src/features/export/exportSentinels.test.ts`(7) 钉住「哪些算哨兵」；
  `tests/e2e/local-flow.spec.ts` 在真实 Chrome 里断言「预览前禁用 → 生成预览后可用」。
  合计 `npm test` **1409 例 / 102 文件**、`npm run test:e2e` **10 例**。

## 1.0.5 用户看验收期已解决：打印版窗口是空白页（用户反馈 ③，v1.3.1 修正）

- **用户看到的现象**（他发的截图）：点「打印 / 另存为 PDF」之后只开出一个**空白标签页**，
  没有下载、也没有打印对话框；界面上的提示却是「导出未完成：浏览器拦截了新窗口」。
- **根因**：代码写的是 `window.open('', '_blank', 'noopener,noreferrer')`。
  带 `noopener` 时浏览器**按规范返回 `null`**，于是我们既拿不到窗口引用（写不进任何内容），
  又会走进「返回 null = 被弹窗拦截」的分支——**窗口其实开着，提示语与事实不符**。
- **修法**：改成普通 `window.open('', '_blank')`，写内容前手动 `opened.opener = null`
  （反向 tabnabbing 防护效果不变）。`AiResultPanel` 的 AI 结果打印版是同一个写法，一并修掉。
- **为什么自动化没拦住**：jsdom 不会真的开窗口；端到端此前只点到「预览 → 四个按钮可用」，
  **没有点过打印那一颗**。与 §1.0.4 属于同一类盲区。
- **回归证据**：`tests/e2e/local-flow.spec.ts` 现在真的点打印，并用 `page.waitForEvent('popup')` 拿到新窗口，
  断言正文含「数据截至日」、正文长度 > 200、`print()` 被调用过（空白页会全部不成立）。
  **修复前这条用例先跑失败**，失败输出里正是那句误导性提示，这就是根因的直接证据。
  另有仓库扫描 `src/features/export/printWindow.test.ts` 禁止 `window.open(` 与 `noopener` 同现
  （扫前剥掉注释；已用临时探针文件验证过它会真的失败）。

## 1.0.6 用户实测暴露：AI 报错把「认证失败」误诊成「参数问题」（v1.3.2 修正）

- **用户看到的现象**（他配好 Key 后第一次真发请求的截图）：红框标题是
  「请求参数被服务端拒绝（可能是模型不支持某个参数，或摘要长度超出模型上下文）」，
  建议是「请检查模型与参数（例如思考模式下的 temperature 会被禁用），或缩小分析范围后重新预览」，
  分类写着 `invalid-params | HTTP 状态：401 | 服务端错误码：invalid_request_error`；
  而同一段里的**服务端说明**是 `Authentication Fails, Your api key: ****ca87 is invalid`。
- **根因**：`errorKindOfCode` 的顺序是「`error.code` 优先、HTTP 状态兜底」，
  而 DeepSeek 对「Key 无效」给的 `code` 是**通用的** `invalid_request_error`（`type` 才写着 `authentication_error`）。
  于是这个通用的 code 先命中 → 判成参数问题 → 提示与建议整套都指错方向。
- **修法**：判定顺序改为 `401 / 402 / 429`（与语义一一对应的三个状态）→ `error.type` → `error.code` → 其余状态兜底；
  同时读服务端的 `type` 字段。`auth` 的建议也改成用户真正能自查的三件事
  （复制是否完整、Key 是否被删除 / 重置、账户是否可用）。口径与反向用例见 `docs/DECISIONS.md` D-098。
- **为什么只有真实调用才暴露**：此前所有 AI 用例用的都是我们**自己编的**错误响应形状
  （`code: 'authentication_error'`），从没喂过真服务端的组合。现已把真实形状写成用例
  （Key 掩码用合成值 `****0000`）：`src/ai/aiResult.test.ts`（新增 4 例）+ `aiClient.test.ts`（新增 1 例）。
- **仍然未验证**：真实 Key 的**成功**路径（余额充足、CORS 通过）依旧没跑通——用户这次唯一到达服务端的一次是 401。

## 1.0.7 用户实测暴露：「HTTP 成功但正文为空」只说「请检查模型与参数」（v1.3.2 修正）

- **用户看到的现象**（同一次会话换好 Key 后的第二次调用）：HTTP 是成功的，但红框写
  「响应里的 content 为空或缺失，本次没有可用结果…**稍后重新预览并确认；若持续为空，请检查模型与参数**」——
  等于没告诉他该改哪里。
- **真正的原因**：他用的模型 `deepseek-flash` **思考模式默认为开启**（我们自己的模型目录里就写着
  `thinkingDefaultEnabled: true`），而推理内容**与正文共用 `max_tokens`** 这一个额度；
  当时 `max_tokens` 是 2048，被推理吃光后正文就是空的。
- **修法（两条）**：① 报错分情况——`finish_reason=length` → 「输出额度用完了」+
  建议关思考模式 / 调大上限；只产出推理内容 → 「本应用不读取推理内容」+ 建议关思考模式；
  两种情况都把 `finish_reason` 与 token 计数（含推理 token 数）写在提示里。
  ② **参数区提前说**：思考模式 = 不指定且该模型默认开启时，直接写明「推理与正文共用最长输出上限」。
  口径见 `docs/DECISIONS.md` D-099。
- **边界**：新代码只检查 `reasoning_content` **在不在**与推理 token **计数**，
  **不读、不存、不显示它的正文**（有用例断言推理正文不出现在错误对象里）。
- **仍未验证**：这次仍然没有拿到**正常结果**——即「调大 max_tokens / 关掉思考模式之后能否成功产出报告」，
  需要用户再试一次才能确认。

## 1.0.8 用户实测暴露：设置里开了 AI，看板仍说「已关闭」（v1.3.3 修正）

- **用户看到的现象**：在设置页打开 AI 开关（临时模式，界面如实提示「配置已在本次会话生效，
  但没能写入本地仓」），切到分析看板后仍写着「AI 深度分析当前是关闭状态」，**预览按钮点不动**。
- **根因**：`loadAiSettings()` 只去仓里读、读不到就回落默认值；临时模式下用户的选择从没进过仓。
  一句话：**提示语承诺「本次会话生效」，代码只做到「本页面生效」。**
- **修法**：偏好加一层**本会话兜底**（写仓失败时记住选择，写仓成功即清掉，仓仍是唯一事实来源），
  并允许**在看板原地配置**（AI 工作区里内联设置页同一个面板），面板每次变更回传给看板。
  口径见 `docs/DECISIONS.md` D-100。

## 1.0.9 用户实测暴露：只是打开清洗预览页就把已提交数据集作废了（v1.3.3 修正）

- **用户看到的现象**：「有时候已经上传了数据，但重新进入分析看板，又要重新确认清洗预览。」
- **根因**：`CleaningEditor` 里写回设置草稿的 `useEffect` **挂载时也会跑**，
  而写回草稿的语义是「设置变了 → 结论作废」。两者叠加＝**只是打开这一页就扔掉数据集**。
- **修法**：首帧只记基线不写回；之后只有真的改了设置才写回（口径见 D-101）。
  回归用例：`CommittedDataset.interaction.test.tsx`（2 例，修前第一条会失败）。
- **仍然存在（未解决，属 §2.3 的同一件事）**：数据集只在内存，
  **刷新页面 / 闲置自动锁定 / 手动锁仓 / 关标签页**之后必须重新导入。

  - 官方端点能否被浏览器**直连**（CORS）**完全未知**：预检响应由我们用例本地合成，
    没有向 `api.deepseek.com` 发过任何真实请求。`curl` 或 Node 请求成功**不等于**浏览器 CORS 通过；
  - Edge / Firefox / WebKit 的行为未测（本机有 Edge，改 `playwright.config.ts` 的 `channel`
    即可复跑，但本轮没有跑），因此**任何跨浏览器兼容性的说法都不成立**。
- **替代做法**：界面与文档一律把它标为「未验证」，绝不写「可以直连」；
  设置页提供「本地 / 自有代理」的显式配置边界（含「代理可见 Key 与摘要」「改地址撤销授权」
  「本仓库不提供代理程序」「不放宽任意域 CSP」）。
- **计划**：用户明确要求时才用真实 Key 做一次合成摘要的付费验证；结果无论成败都写进本文件。
  跨浏览器矩阵与真实托管平台复核属发布前的人工步骤（清单见 `docs/ACCEPTANCE.md` §4）。

### 1.2 首屏包偏大：`index-*.js` 760.09 kB（gzip 231.18 kB）

- **现象**：`App.tsx` 静态 import 了全部页面，因此所有页面（含 ECharts 之外的业务代码）都在首屏包里。
  ECharts 本身已在懒 chunk（`echartsRegister-*.js` 约 543 kB），SheetJS 在 Worker chunk。
  步骤13 又加了 PWA 注册与更新提示（+2.88 kB）。
- **影响**：首次加载偏慢，弱网与低端设备体验受影响；不影响正确性与隐私边界。
- **替代做法**：已知并记录（`docs/DECISIONS.md` D-051）；解析、图表、Dexie 都已在懒边另一侧。
  步骤14 的性能基线与断言把「首屏脚本文件字节」和「首屏不能是懒加载 chunk」钉住了
  （`tests/e2e/performance.spec.ts`）：当前首屏 4 个脚本文件共 **832,572 B**，
  入口不是 `echartsRegister` / `xlsx` / `parse.worker` / `vault-`。
- **计划**：路由级 `lazy()` 是独立一步（D-051），不与 AI 支路混做。

### 1.3 PWA 更新路径与安装体验未在真实浏览器验证

- **现象**：`public/sw.js` 刻意**不自动 `skipWaiting`**：新版停在 `waiting`，界面提示后由用户点击才切换。
  这条路径需要**两个真实版本**才能触发，本轮只验证了首次安装、缓存内容与离线可用。
- **影响**：更新提示何时出现、点「立即更新」后页面是否切到新版本、以及切换后加密仓数据是否仍在，
  目前只有 `pwa/registerServiceWorker.test.tsx`(12) 的注入式验证与设计保证。
  「添加到主屏幕」的真实安装体验同样未验证。
- **替代做法**：注册模块的依赖可注入，因此「不自动更新」「只在真更新时提示」这两条已被单测钉住；
  文案如实说明「更新只换静态资源，不动加密仓」。
- **计划**：发布前用两次连续部署做一次人工验证（`docs/ACCEPTANCE.md` §4 第 6 条）。

- **原现象**：该文件开头的「决策索引」表只列到 D-016，而正文已经写到 D-091（75 条未进索引）。
- **现在的状态（v1.3.0）**：索引已一次性补齐到 **D-001…D-094**（改成从正文小标题批量生成的 78 行），

- **仍然要注意的**：索引里的「状态 / 日期」是按条目标题与所处步骤归的（步骤1–14 = 2026-09-26，

### 2.9 界面上的图表排序 / 横竖方向与「导出的图」不一致（v1.3.0 记录）

- **现象**：用户在界面上看到的柱状图是**按数值从高到低**排的，长名字的图改成**横向条形**；
  而「导出图表图片（PNG）」与「打印 / 另存为 PDF」里的图，是按**报告里的分组顺序**画的、
  每个维度只有 N 与 D 两条序列、并且始终竖排（`exporters/png.ts` 的 `buildChartSpecsFromReport`）。
  同一份数据，**屏幕上的图与文件里的图不是同一张**。
- **为什么暂时不改**：导出图只能消费 `SanitizedReport`（那里的分组标签已经是脱敏结果：HR 是代号、
  小区组已合并、被抑制的组不画）。把「按哪个指标降序、横着还是竖着」从界面传进导出层，
  等于给导出层开一个可以影响出图内容的入口；而排序只是**看图的偏好**，不值得为它扩大这个接口。
  另外导出图刻意只画 N 与 D 两个**计数**序列，不含金额与分位——这是它比界面图更保守的原因。
- **影响**：不影响任何数字（表里的数字两边一致），只影响图的排列与方向；
  已在 PRD 第 8 章的「图表展示规则」里向用户写明，并在导出提示语里说明 PNG / PDF 带图、
  Excel / Markdown 只出数据表。
- **计划**：若用户认为必须一致，做法是给 `ChartSpecInput` 增加一个**纯展示字段**
  （`sortBy` / `orientation`），由导出调用方传入、脱敏与抑制逻辑不动，并补测试证明
  「传入排序不改变类目集合」。未排期。

### 2.10 薪资默认「人民币元/月」下，混有按天计薪 / 外币的行会被标错口径（v1.3.1 记录）

- **现象**：自用户反馈 ① 起，薪资计薪口径的**默认值**是「人民币元/月」。
  如果某份名单里混着「200 元/天」或外币金额的行，而我们没有被告知，这些行会被标成「CNY / 元/月」，
  进而进入同岗薪酬基准与低薪标签的比较。
- **为什么不自动识别**：唯一能自动判断的办法是「金额小于某个数就猜是按天」之类的阈值猜测。
  那会用一个没有依据的经验值去改**口径**——本项目明确不做这种判断（与「不猜状态、不猜单位」同一条纪律）。
  用户选的口径就是他自己的输入，我们只能把它**显示清楚**。
- **现在的缓解措施**：① 清洗口径面板上写清「当前用的是默认值，还没有手动改过：
  名单里有按天计薪或外币的行时请在这里改」；② 明细表与报告里每条记录都带币种与计薪周期，可逐行核对；
  ③ 改成「暂不确定」会立刻禁用待遇对比与低薪标签，并在质量报告里出 `SALARY_UNIT_UNCONFIRMED`。
- **影响**：只有「用户名单里混有非月薪行且没有改口径」这一种情况会出错，且**错在标签而不是金额**
  （金额原样保留、不换算）；已写进 PRD 5.3 与 `docs/DECISIONS.md` D-095。
- **计划**：不做自动识别。若用户希望，可以在清洗预览上加一条**只提示不阻断**的观察项
  （例如「同一份名单的薪资取值跨度超过 20 倍，请确认是否混了按天计薪」），但那需要一个阈值依据，未排期。
